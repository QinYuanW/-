# 物联网 PaaS 云平台 · 数据库表设计说明（11 表）

> 来源：`db/schema.sql`（v1.3，2026-09-17）—— 该文件是**唯一**建表定义源
> 数据库：`iot_platform`　引擎：MySQL 5.7.8+ / InnoDB　字符集：utf8mb4
> 定位：本设计是「设备 → 平台 → 控制台」全链路的数据合同，接口入参出参、EMQX 回调报文、Webhook 解析逻辑均以此为准。
> v1.3 变更：补齐 E3/E4 的 4 张表（device_rule / device_alarm / device_event / device_group）；`device_secret` 64→128。

---

## 0. 总体设计

### 11 张表四类划分

| 分类 | 表 | 特点 |
|---|---|---|
| 账号与资源边界 | project、user | 业务实体表，用 `deleted` 软删（0 未删 1 已删，对齐 MyBatis-Plus @TableLogic） |
| 物模型与设备 | product、device | 业务实体表，`deleted` 软删 |
| 设备分组 | device_group | 业务实体表，但 `deleted` 是 **BIGINT 墓碑（写自身 id）**——见该表说明 |
| 时序与事件流 | device_telemetry、device_log、command | 只增不改不删，靠分区/归档清理，**无 deleted 字段** |
| 规则与告警（E3） | device_rule、device_alarm、device_event | device_rule 为业务实体表（软删）；后两者为事件流表 |

### 核心约定（面试/论文可讲点）

1. **一机一密鉴权**：MQTT 连接时 clientId = device_key，username = device_key，password = device_secret。EMQX auth_http 回调 SpringBoot，查 Redis「auth:v4:{device_key} → secret密文|启用位|product_key」比对（F3 起 secret 以密文入缓存，比对前 AES-GCM 解密）。
2. **不用物理外键**：设备高频上报场景下，外键约束带来行锁竞争；用「逻辑外键 + 索引 + 应用层保证」替代，性能优先。
3. **遥测分区策略**：`device_telemetry` 按月 RANGE COLUMNS 分区（12 个月 + pmax）。滚月必须用 `REORGANIZE` 拆 pmax（不能 ADD PARTITION，pmax 已封顶会报错）。数据量超千万级 / 单设备秒级上报时，V2 迁 TDengine。
4. **软删约定**：业务实体表用 deleted 软删；事件流表只增不改不删。`device_group` 是特例（墓碑写 id，保证分组名可反复复用）。
5. **device_key → device_id 映射**：Webhook 报文带 device_key，SpringBoot 用 Redis 缓存映射，避免每次上报都查 device 表。
6. **command 幂等**：request_id 唯一，同一指令重复下发不会重复执行。
7. **「两层启停」在判断层合成**（F5）：设备能否接入 = `device.status && product.status`，产品停用**不**批量改写子设备 status —— 否则产品恢复后无法还原各设备原状态。
8. **告警存快照、事件走回填**（有意混用）：`device_alarm.rule_name` 存规则名快照（告警是"当时发生了什么"，规则改名不该改写历史）；`device_event` 不存展示名，查询时按产品 TSL 回填（事件是"设备说了什么"，文案属于产品定义，应全局一致）。

## 1. product 产品表

**定位**：物模型（TSL）的入口。一个产品 = 一类设备 = 一份物模型。

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| id | BIGINT UNSIGNED | AUTO_INCREMENT | 主键 |
| product_key | VARCHAR(32) | - | 产品唯一标识（对外，如 p_demo_001），唯一索引 |
| name | VARCHAR(64) | - | 产品名称 |
| project_id | BIGINT UNSIGNED | NULL | 所属项目（逻辑外键 → project.id），v1.2 补充，隔离边界完整 |
| node_type | TINYINT | 1 | 节点类型：1 直连　2 网关　3 子设备 |
| protocol | VARCHAR(16) | 'MQTT' | 接入协议（MVP 固定 MQTT） |
| data_format | VARCHAR(16) | 'JSON' | 数据格式（MVP 固定 JSON） |
| tsl | JSON | NULL | 物模型定义：`{properties:[],services:[],events:[]}` |
| status | TINYINT | 1 | 状态：1 启用　0 停用 |
| deleted | TINYINT | 0 | 软删：0 未删　1 已删 |
| created_at | DATETIME(3) | CURRENT_TIMESTAMP(3) | 创建时间 |
| updated_at | DATETIME(3) | CURRENT_TIMESTAMP(3) ON UPDATE | 更新时间 |

**索引**：PK(id)、UNIQUE `uk_product_key`(product_key)、KEY `idx_project`(project_id)

**设计要点**：
- 物模型 TSL 以 JSON 字段整体存储，MVP 阶段不拆表。
- product_key 是设备与产品关联的对外标识，产品表是设备表的上一级入口。

## 2. device 设备表

**定位**：一机一密三元组（product_key + device_name + device_secret），device_key 是设备接入唯一标识（MQTT 的 clientId / username）。

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| id | BIGINT UNSIGNED | AUTO_INCREMENT | 主键 |
| device_key | VARCHAR(64) | - | 设备唯一标识（MQTT clientId/username），唯一索引 |
| product_key | VARCHAR(32) | - | 所属产品标识（逻辑外键 → product.product_key） |
| device_name | VARCHAR(64) | - | 设备名称（产品内友好名），与 product_key 联合唯一 |
| device_secret | VARCHAR(128) | - | 设备密钥（MQTT password）。**F3 起存 AES-256-GCM 密文**（`v1:` 前缀共 83 字符，故列宽由 64 放宽到 128，见 BUG-28），明文仅在注册响应中一次性返回 |
| project_id | BIGINT UNSIGNED | NULL | 所属项目（逻辑外键 → project.id） |
| online_status | TINYINT | 0 | 在线状态：0 离线　1 在线 |
| last_online_at | DATETIME(3) | NULL | 最近上线时间 |
| last_offline_at | DATETIME(3) | NULL | 最近离线时间 |
| last_ip | VARCHAR(45) | NULL | 最近接入 IP |
| group_id | BIGINT UNSIGNED | NULL | 所属设备分组（E4 已落地，逻辑外键 → device_group.id；NULL = 未分组） |
| tags | VARCHAR(255) | NULL | 标签（JSON 数组） |
| status | TINYINT | 1 | 状态：1 启用　0 停用（F5 停用即拒绝 MQTT 接入，数据全保留） |
| deleted | TINYINT | 0 | 软删：0 未删　1 已删 |
| created_at | DATETIME(3) | CURRENT_TIMESTAMP(3) | 创建时间 |
| updated_at | DATETIME(3) | CURRENT_TIMESTAMP(3) ON UPDATE | 更新时间 |

**索引**：PK(id)、UNIQUE `uk_device_key`(device_key)、UNIQUE `uk_product_name`(product_key, device_name)、KEY `idx_project`(project_id)、KEY `idx_online`(online_status)

**设计要点**：
- device_key 即 MQTT clientId / username，是设备接入唯一凭证（一机一密）。
- `uk_product_name` 保证同一产品下设备名唯一。
- 在线状态冗余在设备表上（`idx_online` 支撑在线列表查询），上下线时间由回调更新。
- `device_secret` 存密文（F3），认证时解密比对；Redis 缓存里也是密文，明文不出库。
- **`status` 与产品 `status` 是两层独立开关**：能否接入 = `device.status && product.status`，
  在判断层实时合成，**不**把产品停用批量写进子设备 —— 产品恢复后各设备原状态才能准确复现（F5）。
- `group_id` 用一对多归属（一个设备只属于一个分组），多维度标记交给 `tags`（E4 的取舍）。

## 3. device_telemetry 设备遥测表（时序数据 · 按月分区）

**定位**：物模型属性上报的落点。MVP 用 MySQL，V2 迁 TDengine（超级表/子表）。

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| id | BIGINT UNSIGNED | AUTO_INCREMENT | 主键（与 ts 联合主键） |
| device_id | BIGINT UNSIGNED | - | 设备主键（逻辑外键 → device.id） |
| property_key | VARCHAR(64) | - | 物模型属性标识（如 temperature） |
| value | VARCHAR(255) | - | 属性值（字符串化存储） |
| value_type | TINYINT | 1 | 值类型：1 数值　2 字符串　3 布尔（v1.2 默认 2→1，主场景为数值型温度） |
| ts | DATETIME(3) | - | 上报时间（设备侧时间），**分区键** |

**主键**：(id, ts)——分区键 ts 必须在主键中，故联合主键。

**索引**：KEY `idx_device_ts`(device_id, ts)、UNIQUE `uk_device_prop_val_ts`(device_id, property_key, value, ts)、KEY `idx_device_prop_ts`(device_id, property_key, ts)

> 唯一键 `uk_device_prop_val_ts` 承担 **D2 幂等去重**（BUG-19/BUG-20）：
> - **键须含 value**（BUG-20 教训）：若仅 `(device_id,property_key,ts)`，QoS0 突发多报文共享同一毫秒 EMQX 时间戳 `ts`，不同上报会被唯一键误判为"同一上报"折叠、`ON DUPLICATE` 静默丢 ~90% 数据；`value` 入键后并发上报 value 不同 → 不误删，真重放 value+ts 全同 → 仍正确去重。
> - `ts` 是分区键，唯一键含 `ts` 以满足"唯一键须含分区列"的约束。
> - ⚠️ 一物两索引分工（已落地）：唯一键 `uk_device_prop_val_ts` 中 `value` 列在中间，无法直接支撑 `(device_id,property_key)+ts 范围` 的索引级裁剪；故补普通索引 `idx_device_prop_ts(device_id,property_key,ts)` **专供查询**（按属性查区间/取最新走它），与幂等唯一键解耦，各自职责单一。

**分区**：`PARTITION BY RANGE COLUMNS (ts)`，预建 2026-08 至 2027-07 共 12 个月分区 + pmax（MAXVALUE）。

**滚月操作（重要）**：必须用 REORGANIZE 拆分 pmax，不能 ADD PARTITION：

```sql
ALTER TABLE device_telemetry REORGANIZE PARTITION pmax INTO (
  PARTITION p202708 VALUES LESS THAN ('2027-09-01'),
  PARTITION pmax    VALUES LESS THAN (MAXVALUE));
```

建议用 MySQL EVENT 或后端定时任务每月 1 号自动执行。

**设计要点**：
- 事件流表：只增不改不删，靠分区/归档清理，无 deleted 字段。
- value 统一字符串化存储，配合 value_type 解释类型，换取存储简单。

## 5. command 指令表（控制下发状态追踪）

**定位**：下发链路状态机——控制台/API → 本表落一条 → EMQX REST API → 设备 → 回报更新状态。

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| id | BIGINT UNSIGNED | AUTO_INCREMENT | 主键 |
| device_id | BIGINT UNSIGNED | - | 目标设备主键（逻辑外键 → device.id） |
| command_type | TINYINT | - | 类型：1 属性下发　2 服务调用 |
| payload | JSON | - | 指令内容（如 `{"switch":true}`，扁平属性映射，与遥测上报同构） |
| status | TINYINT | 0 | 状态：0 待下发　1 已下发　2 已执行　3 失败　4 超时 |
| request_id | VARCHAR(64) | - | 幂等键（每次下发唯一，防重复），唯一索引 |
| sent_at | DATETIME(3) | NULL | 下发时间 |
| ack_at | DATETIME(3) | NULL | 设备回报时间 |
| created_at | DATETIME(3) | CURRENT_TIMESTAMP(3) | 创建时间 |
| updated_at | DATETIME(3) | CURRENT_TIMESTAMP(3) ON UPDATE | 状态机变更时间（v1.2 补充） |

**索引**：PK(id)、UNIQUE `uk_request_id`(request_id)、KEY `idx_device_status_time`(device_id, status, created_at)、KEY `idx_status_sent`(status, sent_at)（v1.2 补充，支撑超时扫描）

**设计要点**：
- request_id 幂等：同一指令重复下发不会产生重复执行。
- 状态机变更走 updated_at 审计，事件流表无 deleted。
- `idx_status_sent` 专门支撑「扫描超时未确认指令」的后台任务。

## 8. device_group 设备分组表（E4）

**定位**：按运维维度批量组织设备（如"按位置/用途分几组"）。与「产品」（设备的能力定义）**正交**。

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| id | BIGINT UNSIGNED | AUTO_INCREMENT | 主键 |
| name | VARCHAR(64) | - | 分组名称，与 deleted 联合唯一（软删后可复用） |
| description | VARCHAR(255) | NULL | 分组描述 |
| sort_order | INT | 0 | 展示排序（越小越前） |
| deleted | **BIGINT UNSIGNED** | 0 | 软删墓碑：0 未删；已删则写**自身 id** |
| created_at | DATETIME(3) | CURRENT_TIMESTAMP(3) | 创建时间 |
| updated_at | DATETIME(3) | CURRENT_TIMESTAMP(3) ON UPDATE | 更新时间 |

**索引**：PK(id)、UNIQUE `uk_group_name`(name, deleted)、KEY `idx_sort`(sort_order)

**设计要点**：
- **刻意平铺一级，不做树形**：设备分组的实际用法是"分几组"，层级带来的递归查询与前端树组件成本换不来对应价值；日后确需层级，加 `parent_id` 即可平滑扩展。
- **`deleted` 是 BIGINT 且墓碑写自身 id（不是 0/1）** —— 这是全库唯一的特例，且是必须的：
  它配合唯一键 `uk_group_name(name, deleted)`，保证「删除后名称可复用」对**任意多次**删除都成立。
  若用 0/1，第二次删除同名分组就会撞上 `(name, 1)` 的唯一键（实测报 1062）。所以类型是 BIGINT 而非其他表的 TINYINT，**是有意为之，不是笔误**。
- 设备归属走 `device.group_id`（一对多）而非中间表：一个设备同时属于多个分组在运维语义上无意义。
- **删除分组不删设备**：删组时把组内设备的 `group_id` 置空（回到"未分组"），避免"手滑删个分组把设备一起干掉"。

## 9. device_rule 阈值规则表（E3）

**定位**：告警规则的配置面。规则由后端在**每条遥测落库后**评估，命中即生成告警；`action_type=1` 时联动下发指令（如「温度 > 50 自动关断」）。

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| id | BIGINT UNSIGNED | AUTO_INCREMENT | 主键 |
| name | VARCHAR(64) | - | 规则名称 |
| product_key | VARCHAR(32) | - | 所属产品（规则按产品生效） |
| device_key | VARCHAR(64) | NULL | 限定单台设备；NULL/空 = 作用于该产品下**所有**设备 |
| property_key | VARCHAR(64) | - | 监测的属性标识（应对应产品物模型） |
| operator | VARCHAR(4) | - | 比较运算符：`>` `>=` `<` `<=` `==` `!=` |
| threshold | DECIMAL(18,4) | - | 阈值 |
| level | TINYINT | 2 | 告警级别：1 严重　2 一般　3 提示 |
| alarm_type | VARCHAR(32) | '规则告警' | 告警类型（展示分组用） |
| action_type | TINYINT | 0 | 命中动作：0 仅告警　1 告警并下发指令 |
| action_payload | JSON | NULL | `action_type=1` 时下发的 payload（属性名→值） |
| cooldown_sec | INT | 60 | 抑制窗口：同规则同设备 N 秒内只告警一次 |
| enabled | TINYINT | 1 | 状态：1 启用　0 停用 |
| deleted | TINYINT | 0 | 软删：0 未删　1 已删 |
| created_at | DATETIME(3) | CURRENT_TIMESTAMP(3) | 创建时间 |
| updated_at | DATETIME(3) | CURRENT_TIMESTAMP(3) ON UPDATE | 更新时间 |

**索引**：PK(id)、KEY `idx_product_enabled`(product_key, enabled, deleted)

**设计要点**：
- **`cooldown_sec` 不是可选项**：设备每秒上报，温度持续超标时若不抑制，一分钟就能刷出 60 条重复告警。冷却用 Redis `SETNX`（键 `rule:cd:{ruleId}:{deviceId}`）做原子窗口判定。
- **`action_payload` 是 JSON 列，必须落 NULL 而非空串**：空串不是合法 JSON，MySQL 直接报 3140。
- ⚠️ **规则变更必须清缓存**：评估路径为省一次 SELECT 把规则缓存在 Redis `rules:{product_key}`（TTL 60s）。改规则不清缓存，就会出现"界面上改了、上报还是老规则"的假故障；改 `product_key` 时新旧两个产品都要清。规则管理接口（契约 §12）已处理。
- `device_key` 为空 = 作用于全产品，这是"产品级规则"的实现方式。

## 10. device_alarm 告警记录表（E3）

**定位**：规则命中的落点，含「未处理 → 已处理」状态流转。

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| id | BIGINT UNSIGNED | AUTO_INCREMENT | 主键 |
| device_id | BIGINT UNSIGNED | - | 设备主键（逻辑外键 → device.id） |
| rule_id | BIGINT UNSIGNED | NULL | 命中的规则；规则删除后成为孤儿引用 |
| alarm_type | VARCHAR(32) | '规则告警' | 告警类型 |
| level | TINYINT | 2 | 告警级别：1 严重　2 一般　3 提示 |
| rule_name | VARCHAR(64) | NULL | **规则名快照**（冗余存档，规则删除后仍可读） |
| content | VARCHAR(512) | NULL | 告警正文（含命中值与阈值，便于事后追溯） |
| status | TINYINT | 0 | 处理状态：0 未处理　1 已处理 |
| handled_at | DATETIME(3) | NULL | 处理时间 |
| created_at | DATETIME(3) | CURRENT_TIMESTAMP(3) | 产生时间 |

**索引**：PK(id)、KEY `idx_device_time`(device_id, created_at)、KEY `idx_status_time`(status, created_at)

**设计要点**：
- **独立成表而不复用 `device_log`**：告警有结构化字段与「未处理→已处理」状态流转；塞进 `device_log` 的 1024 字符自由文本里，筛选与统计会退化成字符串解析。
- **`rule_name` 存快照而不是查询时 JOIN 回填**：告警回答的是"当时发生了什么"，规则后来改名/删除不该改写历史。这也让规则可以做逻辑删而不破坏历史告警可读性（`rule_id` 变孤儿引用，无外键，物理无害）。
- 事件流表：只增不改不删（除 `status`/`handled_at` 的处理流转），无 `deleted`。

## 11. device_event 设备事件表（E3）

**定位**：设备主动上报的事件落点（`up/{device_key}/event` → EMQX 规则 → `POST /api/v1/events`）。

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| id | BIGINT UNSIGNED | AUTO_INCREMENT | 主键 |
| device_id | BIGINT UNSIGNED | - | 设备主键（逻辑外键 → device.id） |
| event_key | VARCHAR(64) | - | 事件标识（对应产品物模型 `events[].key`） |
| params | JSON | NULL | 事件参数原文 |
| ts | DATETIME(3) | - | 事件发生时间（设备侧时间） |
| created_at | DATETIME(3) | CURRENT_TIMESTAMP(3) | 入库时间 |

**索引**：PK(id)、KEY `idx_device_ts`(device_id, ts)、KEY `idx_device_event_ts`(device_id, event_key, ts)

**设计要点**：
- **展示名与类型不入库**，查询时按产品 TSL 回填。理由：事件是"设备说了什么"，展示文案属于产品定义，改文案应当全局一致；若把展示名快照进库，改一次文案历史数据就前后不一致。
  （与 `device_alarm.rule_name` 存快照的策略**相反且有意为之** —— 见 §0 核心约定第 8 条。）
- 事件流表：只增不改不删，无 `deleted`。
- 设备上报的**参数原文**整体存 JSON，不做字段级拆解：事件参数随物模型演化，拆列会频繁 ALTER。

## 附：表间关系一句话总结

```
project (1) ──< product (1) ──< device (1) ──< device_telemetry
    │               │              │
    │               │              ├──< device_log
    │               │              ├──< command
    │               │              ├──< device_alarm
    │               │              └──< device_event
    │               └──< device_rule ──< device_alarm（rule_id，可空）
    └── project (1) ──< device（project_id 同时挂在 device 上）

device_group (1) ──< device（group_id，可空 = 未分组）
```

- product、device 通过 project_id 归属 project（资源隔离）。
- device 通过 product_key 归属 product；再通过 group_id 归属 device_group（E4，一个设备只属一个组）。
- device_rule 通过 product_key 按产品生效，可选 `device_key` 收窄到单台设备（E3）。
- device_telemetry / device_log / command / device_alarm / device_event 通过 device_id 归属 device（事件流）。
- device_alarm 通过 rule_id 指回命中它的规则；规则删除后成孤儿引用（`rule_name` 快照保证历史仍可读）。
- device_event 的 `event_key` 逻辑上指向产品 TSL 的 `events[].key`（不落库为外键，展示名查询时回填）。
