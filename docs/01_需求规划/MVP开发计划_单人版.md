# MVP 开发计划（单人版）

> 面向：独立开发者，1 人完成整个物联网 PaaS 平台 MVP
> 前提：需求与技术选型已定稿，见《物联网PaaS云平台需求分析文档》V1.1
> 核心目标：跑通「ESP32 上报温度 → 存库 → 网页查看 → 网页下发控灯」最小闭环

---

## 0. 单人开发的生存法则

一个人做完整个平台，最大的敌人不是技术，而是两样东西：

1. **范围蔓延**——写着写着就想加功能，结果 MVP 永远做不完。
2. **上下文切换**——上午写 Java、下午调 ESP32、晚上配 EMQX，每次切换都要重新进入状态，效率暴跌。

所以定下三条铁律：

> **① 每个阶段只推一条主线，绝不并行。**
> **② 能复用现成的绝不自己写**（EMQX Dashboard 看连接、MQTTX 调试、MySQL Workbench 看数据）。
> **③ 先打通端到端闭环，再谈功能完整。**

---

## 1. 一句话总览

- 全职：**2~3 周**；兼职（每天 2~3 小时）：**4~6 周**。
- 里程碑只有三个：**数据能存** → **指令能下发** → **网页能看能控**。

---

## 2. 砍掉什么（单人版专属）

| 原 MVP 功能 | 单人版处理 | 理由 |
|------------|-----------|------|
| 完整物模型模板库 | 只做「属性」一类（温度/开关），服务/事件后置 | 模板库是体力活，不影响闭环 |
| 可视化规则引擎 | 用 EMQX Webhook 直推，不配规则 | 规则引擎是另一个子系统 |
| 设备影子 / 离线缓存 | 推迟到 V2 | 场景出现再补 |
| 多租户 / 角色权限 | 单租户 + 单管理员账号 | 一个人验证用不上 |
| OpenAPI 完整版 | 只留「设备查询」+「下发」两个接口 | 先验证核心链路 |
| 复杂仪表盘 | 一个极简页面 | 前端最耗时间，最后做 |

> 核心原则：**MVP 的使命是"验证这条路走得通"，不是"功能齐全"。**

---

## 3. 阶段路线图

### 阶段 0：地基（1 天）

**目标**：环境能跑，看懂 EMQX。

- [ ] Docker Compose 拉起 EMQX + MySQL + Redis
- [ ] 用 MQTTX 连 EMQX，发布/订阅，验证能收发
- [ ] 熟悉 EMQX Dashboard（看连接、消息、以及 HTTP 认证 / Webhook 配置入口）

**完成标志**：MQTTX 能收发消息，Dashboard 能看到连接。

---

### 阶段 1：鉴权 + 上报 + 存库（3~4 天，全项目核心）

**目标**：设备能连上、数据能落库。

- [ ] SpringBoot 单 module 骨架（Spring Web + MyBatis-Plus + Redis，不搞微服务）
- [ ] 建表：`product`、`device`、`device_telemetry`、`device_log`
- [ ] 设备鉴权接口（EMQX HTTP 认证 → 校验 device_key，只查 Redis 不落库）
- [ ] Webhook 接收接口（接收上报 → 解析 JSON → 存 MySQL）
- [ ] ESP32 最小固件（esp-mqtt 连 EMQX + 定时上报温度）

**完成标志**：ESP32 上电，MySQL 的 `device_telemetry` 表里温度数据持续写入。

> ⚠️ 这是全项目最关键的一步。这一步通了，后面都是"加功能"；这一步卡住，整个项目就卡住。

---

### 阶段 2：查询 + 下发（2~3 天）

**目标**：能查数据、能控设备。

- [ ] 设备查询接口（列表 / 详情 / 最新数据）
- [ ] 下发接口（Java → EMQX REST API `/api/v5/publish` → 设备）
- [ ] ESP32 订阅指令 topic，收到后执行（如 GPIO 控制 LED 亮灭）

**完成标志**：curl 下发指令，ESP32 的 LED 响应。

---

### 阶段 3：极简控制台（3~4 天）

**目标**：网页能看能控。

- [ ] Vue 单页：登录 → 设备列表 → 实时数据 → 下发按钮
- [ ] 数据刷新用轮询（先不搞 WebSocket，够用）

**完成标志**：浏览器里能看温度曲线、点按钮控 LED。

**轮询方案（MVP 实时数据的唯一机制）**

前端不用 WebSocket，用 `setInterval` 定时调 REST API 拉数据。核心接口只留 4 个：

| 接口 | 方法 | 作用 | 轮询间隔 |
|------|------|------|---------|
| `/api/v1/devices` | GET | 设备列表（含在线状态） | 5s |
| `/api/v1/devices/{id}/telemetry/latest` | GET | 某设备最新遥测数据（温度/开关） | 3s |
| `/api/v1/devices/{id}/telemetry?start=&end=` | GET | 历史数据（画曲线用，进详情页再拉） | 进入页面拉一次 |
| `/api/v1/devices/{id}/commands` | POST | 下发指令（body: `{"property":"led","value":1}`） | 点击触发 |

前端骨架（Vue 3 + axios）：

```js
// 最新数据：每 3s 拉一次
const latest = ref({})
const t1 = setInterval(async () => {
  const { data } = await axios.get(`/api/v1/devices/${deviceId}/telemetry/latest`)
  latest.value = data
}, 3000)

// 设备列表（含在线状态）：每 5s 拉一次
const deviceList = ref([])
const t2 = setInterval(async () => {
  const { data } = await axios.get('/api/v1/devices')
  deviceList.value = data
}, 5000)

// 组件卸载时清理定时器，防止内存泄漏
onUnmounted(() => { clearInterval(t1); clearInterval(t2) })
```

> ⚠️ 记住三个坑：① 定时器必须在 `onUnmounted` 里清理，否则切换路由后还在空转；② 请求失败要静默重试，别弹窗打断用户；③ 后端对应接口只查 Redis/MySQL，不落库、不做复杂逻辑，保证轮询压不垮。
>
> 什么时候升级 WebSocket：出现"秒级实时刷新"需求（告警弹窗、大屏动画）或轮询请求量打满后端时，V2 再补（见需求文档决策记录 #8）。

---

### 阶段 4：收尾 + 压测（2~3 天）

- [ ] 设备注册（单个 + CSV 批量导入）
- [x] 上下线状态（心跳超时扫描：30s 扫描、60s 超时 → 写 device_log；设计决策：以心跳扫描替代 EMQX 上下线事件，实现更简单且对异常断线同样有效）
- [ ] 简单压测（脚本模拟 100 台设备同时上报）

## 4. 技术清单（够用就行，别贪多）

| 层 | 选型 | 说明 |
|----|------|------|
| 后端 | SpringBoot 3.2 + MyBatis-Plus + MySQL + Redis | **一个 module**，不拆微服务 |
| 接入 | EMQX 5.8（HTTP 认证 + Webhook） | 复用其 Dashboard |
| 设备 | ESP32 + esp-mqtt | 你的强项 |
| 前端 | Vue3 + Element Plus | 阶段 3 才动，甚至可以再后置 |
| 调试 | MQTTX、EMQX Dashboard、MySQL Workbench、Postman | 全是现成工具 |

---

## 5. 单人特有的坑（务必看）

1. **前端最耗时间，可后置甚至砍掉**——MVP 阶段用 `curl` + EMQX Dashboard + MySQL Workbench 就能完成验证，前端等到核心闭环稳定后再补。
2. **设备"连不上"最耗时间**——务必先用 MQTTX 验证 EMQX 本身没问题，再上真实 ESP32。定位问题时，先排除"是 EMQX 的问题还是设备的问题"。
3. **别一上来就写"通用物模型引擎"**——先用写死的温度字段跑通整条链路，再抽象成物模型。过早抽象是单人开发最大的时间黑洞。
4. **一个 module 走天下**——不要为了"架构漂亮"拆微服务，那是在给自己挖运维的坑。

---

## 6. 进度追踪建议

用 5 个里程碑（阶段 0~4）当"灯塔"，每完成一个就更新一次。别用"今日完成 X 个小任务"这种粒度，会陷入细节。

**每阶段结束只问自己一句：闭环还在往前推进吗？** 在，就继续；不在，停下来查。
