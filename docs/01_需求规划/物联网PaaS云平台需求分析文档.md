# 物联网 PaaS 云平台需求分析文档

> 版本：V1.1（已按 MVP 技术决策更新：Java/SpringBoot + MySQL 主栈，MQTT 单协议先行）  
> 定位：自研物联网 PaaS 云平台（对标 OneNET / 阿里云 IoT / 腾讯云 IoT）  
> 方向：向下接入海量设备，向上开放数据与能力接口，支撑行业应用快速开发  
> 团队技术背景：STM32 / ESP32 嵌入式开发、MQTT、WebSocket、FreeRTOS、LVGL

---

## 1. 项目背景与目标

### 1.1 行业背景与市场痛点

物联网正在从"单点试点"走向"规模化落地"，但设备接入云平台这一环始终是行业最大的效率黑洞。核心痛点集中在三处：

**① 设备碎片化（Device Fragmentation）**

- 芯片/模组千差万别：STM32（裸机/FreeRTOS）、ESP32（ESP-IDF/Arduino）、Linux 网关（OpenWrt/Buildroot），每一种都有独立的 SDK 与资源约束。
- 通信协议不统一：同一行业里，A 厂商用 MQTT，B 厂商用 CoAP，C 厂商用私有 TCP 协议，D 厂商的 PLC 走 Modbus RTU。
- 结果：应用开发每接入一个客户，就要重写一遍协议适配层。

**② 协议不统一（Protocol Chaos）**

- 缺乏统一的物模型（TSL）标准，同一个"温度"字段在不同设备里叫 `temp` / `temperature` / `T` / `value_1`。
- 数据格式混乱：JSON / 二进制 / 自定义帧格式并存，应用层解析成本极高。
- 结果：数据孤岛，跨设备、跨厂商的数据融合几乎不可行。

**③ 开发周期长（Long Development Cycle）**

- 一个简单的"采集数据 → 展示 → 控制"场景，自建方案需要：选型 Broker、搭数据库、写鉴权、做管理后台、做 App 对接，动辄 3~6 个月。
- 缺少成熟的 PaaS 底座，重复造轮子，人力都消耗在基础设施而非业务上。

**市场机会**：大厂云（阿里、腾讯、华为）IoT 平台功能全但**绑定生态、私有化成本高、对中小团队重**；OneNET 作为运营商系平台，轻量但**定制能力有限、数据不出企业内网受限**。这给"轻量、可私有化、低成本"的自研 PaaS 留出了明确空间。

### 1.2 项目目标

建设一个**中立、可私有化部署、模块化**的物联网 PaaS 平台，让团队用最小成本完成设备接入 → 数据管理 → 应用开放的全链路。

具体目标拆解：

| 目标维度 | 目标描述                                                                      |
| ---- | ------------------------------------------------------------------------- |
| 设备接入 | 支持 MQTT / CoAP / HTTP / TCP / Modbus 多协议，提供 C/Java/Python/Node.js 四语言 SDK |
| 数据管理 | 统一物模型（TSL），时序数据入库，规则引擎灵活流转                                                |
| 能力开放 | RESTful OpenAPI + WebSocket 实时订阅，让应用开发者像调普通 API 一样用 IoT                   |
| 运维友好 | 私有化一键部署（Docker/K8s），平台自身可观测                                               |
| 差异化  | 轻量（< 20 个微服务）、低成本、数据可完全私有化                                                |

### 1.3 成功指标（KPI / 北极星指标）

| 指标       | 目标值（第一阶段）              | 说明                 |
| -------- | ---------------------- | ------------------ |
| 设备接入量    | ≥ 10 万设备               | 架构设计预留 100 万+ 扩展能力 |
| 并发连接数    | 单节点 ≥ 10 万 MQTT 长连接    | EMQX 集群水平扩展至百万级    |
| 数据吞吐     | ≥ 10 万条消息/秒            | 指设备上报写入消息总线        |
| 时序数据写入   | ≥ 1000 条/秒（MVP 单机 MySQL）        | V2 演进 TDengine   |
| 平台可用性    | ≥ 99.9% SLA            | 月故障时长 < 43.2 分钟    |
| API 响应时间 | 平均 < 200ms，P99 < 500ms | 控制面 REST API       |
| 设备接入效率   | 新设备接入 ≤ 1 人天           | 通过标准物模型 + SDK 达成   |

## 2. 用户分析

### 2.1 用户画像

#### 画像 1：设备开发者（嵌入式工程师）

- **背景**：熟悉 STM32/ESP32，写过 FreeRTOS 任务，接触过 MQTT，但对云平台后端不熟。
- **核心痛点**：
  - 没有一套"拿来即用"的接入 SDK，每次都要手写 MQTT 连接、鉴权、断线重连、心跳。
  - 设备端资源紧张（RAM 从几 KB 到几 MB），SDK 必须轻量、无侵入。
  - 调试困难：看不到设备侧报文、上下线原因、消息链路。
- **诉求**：SDK 简单、文档清晰、有在线调试工具、能快速定位"为什么连不上/为什么丢消息"。

#### 画像 2：应用开发者（后端/前端/全栈）

- **背景**：熟悉 REST API、WebSocket，想快速做行业应用（小程序/大屏/后台），不想碰设备协议细节。
- **核心痛点**：
  - 不知道设备数据在哪、什么格式，物模型不统一导致解析成本高。
  - 需要实时推送却拿不到稳定的 WebSocket/订阅接口。
  - API 文档缺失，鉴权方式不明确。
- **诉求**：统一物模型、标准 REST API、Swagger 文档、WebSocket 实时订阅、清晰的限流与鉴权规则。

#### 画像 3：企业运维人员

- **背景**：负责系统稳定运行，关注连接数、告警、故障恢复。
- **核心痛点**：
  - 平台自身可观测性差：看不到连接数趋势、消息堆积、节点 CPU/内存。
  - 设备掉线、异常上报后通知不及时。
  - 缺少操作审计，出了问题难追溯。
- **诉求**：设备在线率监控、告警通知（钉钉/飞书/邮件/Webhook）、平台监控大盘、操作审计日志。

#### 画像 4：企业管理者（项目负责人/方案商老板）

- **背景**：关心成本、交付周期、数据安全。
- **核心痛点**：
  - 用大厂云 IoT 平台，数据在别人手里，私有化成本高、受生态绑定。
  - 交付客户时，每个项目都要重新搭一套。
- **诉求**：低成本私有化部署、数据不出内网、多租户隔离、可对外交付/白标。

### 2.2 典型使用场景

1. **设备调试**：设备开发者注册产品 → 定义物模型 → 用 SDK 接入 → 在控制台"设备调试"页实时查看上报/下发报文，验证物模型与通信链路。
2. **批量部署**：方案商为客户批量注册设备（CSV 导入/批量生成 DeviceSecret），按项目/分组管理，一键下发配置。
3. **数据监控**：运维/应用方在仪表盘实时查看设备遥测数据，历史数据按时间范围查询、折线图/仪表盘展示。
4. **远程控制**：应用通过 API 或控制台下发属性/调用服务，远程控制设备（开关、参数调整），支持离线指令缓存。
5. **OTA 升级**：上传固件包 → 创建升级任务（单设备/批量/灰度）→ 监控升级进度 → 失败自动回滚。
6. **告警联动**：配置阈值告警（如温度 > 80℃），触发后通过钉钉/飞书/短信通知，并关联规则引擎联动其他设备。

## 3. 系统架构设计

### 3.1 整体架构（三层）

```
┌─────────────────────────────────────────────────────────────┐
│                        应用层（Application Layer）              │
│   行业应用(小程序/大屏/后台)   控制台(Web)    OpenAPI(REST/WS)  │
└──────────────────────────────┬──────────────────────────────┘
                               │ 鉴权/限流/API 网关
┌──────────────────────────────┴──────────────────────────────┐
│                        平台层（Platform Layer）                 │
│  ┌──────────┬──────────┬──────────┬──────────┬──────────┐   │
│  │ 设备管理  │ 物模型TSL │ 规则引擎  │ 告警引擎  │ 账号权限  │   │
│  ├──────────┼──────────┼──────────┼──────────┼──────────┤   │
│  │ 数据存储  │ 设备影子  │ OTA服务   │ 可视化    │ 运维监控  │   │
│  └──────────┴──────────┴──────────┴──────────┴──────────┘   │
│      消息总线(Kafka/MQ) ── 时序库(TDengine) ── 关系库(PG)     │
└──────────────────────────────┬──────────────────────────────┘
                               │ 协议适配/认证
┌──────────────────────────────┴──────────────────────────────┐
│                        接入层（Access Layer）                   │
│   MQTT Broker(EMQX)   CoAP/HTTP 网关   TCP 私有协议网关   Modbus │
│   ── 设备认证(一机一密/一型一密/Token) ── TLS 加密 ──          │
└───────────────────────────────────────────────────────────────┘
```

**分层职责**：

| 层级  | 职责                               | 关键组件              |
| --- | -------------------------------- | ----------------- |
| 接入层 | 协议解析、设备认证、连接管理、消息接入              | EMQX、协议网关服务       |
| 平台层 | 设备/产品/物模型管理、数据存储、规则引擎、控制下发、告警、权限 | 微服务集群             |
| 应用层 | 面向应用开发者的能力开放 + 控制台 + 行业应用        | API Gateway、控制台前端 |

> **MVP 实际启用范围**：接入层仅 MQTT（EMQX）；数据层 MySQL + Redis（V2+ 才引入 Kafka/TDengine）；平台层为 SpringBoot 单体应用（非微服务）。下方表格保留的是目标形态，MVP 先跑通主干。

### 3.2 技术栈建议

| 模块          | 推荐方案                                              | 备选                        | 选型理由                                  |
| ----------- | ------------------------------------------------- | ------------------------- | ------------------------------------- |
| 消息队列 Broker | **EMQX 5.x**（MQTT）                                | Mosquitto（开发调试）、VerneMQ   | 高并发、规则引擎/数据桥接内置、运维成熟                  |
| 数据流转 MQ     | **HTTP Webhook**（MVP）→ Kafka 3.x（V2+）                                     | RabbitMQ、RocketMQ         | MVP 用 EMQX Webhook 直推 Java；量大后演进 Kafka                      |
| 时序数据库       | **MySQL 8.0**（MVP）→ TDengine 3.x（V2+）                                  | InfluxDB 2.x、TimescaleDB  | MVP 用 MySQL 先跑通；数据量大后迁 TDengine（压缩比~10:1）             |
| 关系数据库       | **MySQL 8.0**                                 | PostgreSQL 16                 | 元数据/账号/物模型/设备数据，MVP 统一用 MySQL                   |
| 缓存          | **Redis 7.x**                                     | —                         | 设备在线状态、Token 缓存、分布式锁                  |
| 后端语言        | **Java 17 + Spring Boot 3.2**（MVP 全栈）                             | Go 1.22（V2 高并发接入层） | MVP 用团队最熟的 SpringBoot 快速交付；高并发接入 V2 再评估 Go     |
| 微服务框架       | **Spring Boot 3.2（单体起步）** → Spring Cloud Alibaba | —                         | MVP 单应用起步，V2 按需拆分                            |
| API 网关      | **Kong / APISIX**                                 | Nginx + Lua               | APISIX 性能好、动态路由、限流插件全                 |
| 前端框架        | **Vue 3 + Vite + TypeScript**                     | React 18 + Ant Design     | Element Plus 组件全、上手快                  |
| 图表库         | **ECharts 5**                                     | —                         | 大屏/仪表盘/折线图                            |
| 规则引擎        | EMQX Rule Engine + **自研轻量规则服务**                   | Flink CEP                 | MVP 阶段用 EMQX 内置 + 自研，复杂流式处理后期再上 Flink |
| 容器编排        | **Docker Compose**（MVP）→ **Kubernetes 1.28**（生产）  | —                         | 渐进式                                   |

### 3.3 部署架构（三阶段演进）

**阶段一：单机（开发/测试/POC）**

- Docker Compose 一键拉起：EMQX + MySQL + Redis + SpringBoot 单体服务 + 前端。
- 适合 1000 台以内设备的小型验证，1 台 8C16G 服务器即可。

**阶段二：MQTT 集群（中小规模生产）**

- EMQX 3 节点集群 + HAProxy/Nginx Stream 做 TCP 负载均衡。
- 关系库/时序库/Redis 独立部署或主从。
- 支撑 10 万级并发连接。

**阶段三：分布式（大规模）**

- Kubernetes 托管微服务（Deployment 多副本 + HPA 自动伸缩）。
- EMQX 集群横向扩展，Kafka 集群承载数据流，TDengine 集群。
- 接入层、平台层、数据层全部可水平扩展，支撑百万级设备。

### 3.4 MVP 技术实现链路（6 步数据流）

MVP 先跑通一条「设备 → 平台 → 控制台」的最小闭环，技术链路如下：

```
① 设备接入    ESP32/STM32 通过 MQTT（TLS）连接 EMQX
② 连接鉴权    EMQX 触发 HTTP 认证，调用 SpringBoot 接口校验 device_key
③ 数据上报    设备发布温度等属性，EMQX 规则引擎/Webhook 将报文 HTTP 推送给 Java 服务
④ 数据落库    Java 解析物模型 TSL，写入 MySQL（遥测数据）/ Redis（在线状态、缓存）
⑤ 控制台操作   Web 控制台调 Java 接口查看设备状态、下发控制指令
⑥ 指令下发    Java 调 EMQX REST API（/api/v5/publish），EMQX 转发给目标设备
```

数据流拓扑：

```
设备(ESP32/STM32) ──MQTT──▶ EMQX ──HTTP认证──▶ SpringBoot(校验 key)
                              │
                              │ Webhook(HTTP 推送报文)
                              ▼
                         SpringBoot ──▶ MySQL / Redis
                              ▲
                              │ REST API
控制台(Web) ──────────────────┘
                              │ 下发指令
                              ▼
                         EMQX REST API ──MQTT──▶ 设备
```

**关键点**：
- 鉴权走 EMQX HTTP 认证插件（`emqx_auth_http`），MVP 只做一机一密，鉴权结果在 Redis 缓存。
- 数据流转 MVP 用 Webhook 直推（简单），V2 演进 EMQX 规则引擎 → Kafka。
- 下发统一走 EMQX REST API，控制台与 Java 服务共用这条链路，指令状态在 Java 侧追踪。

## 4. 功能需求（P0/P1/P2 分级）

> 分级原则：P0 = MVP 必须，P1 = 第二阶段，P2 = 增强/优化。

---

### 4.1 设备接入模块（P0）

**功能描述**：提供多协议设备接入能力，完成设备认证、连接管理、数据采集。

**① 多协议支持（长期优先级；MVP 仅 MQTT，CoAP/HTTP/TCP/Modbus 均 V3 补齐）**

| 优先级 | 协议             | 说明                          | 适用场景                |
| --- | -------------- | --------------------------- | ------------------- |
| P0  | **MQTT**       | 基于 EMQX，支持 MQTT 3.1.1 / 5.0 | 主力协议，绝大多数设备         |
| P0  | **TCP 私有协议**   | 自研 TCP 网关，支持自定义帧解析插件        | 存量私有设备、Modbus 转 TCP |
| P1  | **HTTP/HTTPS** | 数据上报、API 调用                 | 低功耗/无长连接的设备         |
| P1  | **CoAP**       | 基于 UDP，轻量                   | 低功耗窄带设备（NB-IoT）     |
| P2  | **Modbus**     | Modbus RTU/TCP 网关           | 工业 PLC、传感器          |

**② 设备认证方式**

| 认证方式         | 说明                                             | 适用场景       |
| ------------ | ---------------------------------------------- | ---------- |
| **一机一密**     | 每台设备独立 ProductKey/DeviceName/DeviceSecret，动态生成 | 生产设备，安全要求高 |
| **一型一密**     | 同产品共享密钥，设备首次激活时动态注册获取独立密钥                      | 量产设备，简化烧录  |
| **Token 认证** | 平台签发临时 Token，SDK 携带 Token 接入                   | 临时授权、第三方接入 |

**③ 接入 SDK 规划**

| 语言              | 优先级 | 目标平台                       | 要点                                    |
| --------------- | --- | -------------------------- | ------------------------------------- |
| **C SDK**       | P0  | STM32/ESP32/FreeRTOS/Linux | 轻量（ROM < 30KB）、断线重连、心跳、QoS、TLS、OTA 支持 |
| **Python SDK**  | P0  | 树莓派/Linux 网关               | 快速原型、脚本设备                             |
| **Java SDK**    | P1  | Android/Java 后端            | 与 mqtt client 封装                      |
| **Node.js SDK** | P1  | Node 后端/边缘                 | 与 MQTT.js 封装                          |

> C SDK 与团队 STM32/ESP32/FreeRTOS 技术栈直接匹配，是 MVP 重点。可基于 `paho.mqtt.embedded-c` 或 `esp-mqtt` 封装，做一层"连接 + 物模型 + OTA"的上层抽象。

**④ 网关与子设备拓扑管理**

- 支持"网关设备"下挂"子设备"（如 Modbus 网关挂多个传感器）。
- 网关代理子设备认证与消息转发，支持拓扑查询（`parent-child` 关系）。
- 子设备可独立拥有物模型，通过网关透传上下行。

---

### 4.2 设备管理模块（P0）

**① 产品管理**

- 产品创建：定义产品名称、品类、节点类型（直连/网关/子设备）、接入协议、数据格式。
- **物模型定义（核心）**：功能定义分三类——
  - **属性（Property）**：设备状态值，如温度、开关（读写/只读）。
  - **服务（Service）**：设备可执行的操作，如"重启""校准"，含入参/出参。
  - **事件（Event）**：设备主动上报的告警/通知，如"温度超限"。
- 支持标准物模型模板库（温湿度、开关、电表、网关等通用模板）+ 自定义扩展。

**② 设备管理**

- 设备注册：单个注册 / CSV 批量导入 / 一型一密动态注册。
- 上下线状态：实时维护在线/离线状态，记录最近上线时间、IP、心跳。
- **设备影子（Device Shadow）**：云端保存设备期望状态与上报状态，设备离线时可缓存下发指令，上线后同步。
- 设备分组：按项目/区域/客户分组，支持组内批量操作。
- 标签：设备自定义标签，用于检索、批量控制、规则过滤。

**③ 物模型（TSL）标准化**

- TSL 采用 JSON 描述（类似阿里云 TSL 结构），包含属性/服务/事件的定义。
- 物模型版本管理：修改物模型不影响历史数据查询。
- 标准模板库 + 自定义，降低新设备接入成本。

---

### 4.3 数据存储与流转模块（P0）

**① 时序数据存储**

- 设备属性上报数据 → EMQX Webhook 推给 Java 服务 → 解析物模型 TSL → 存 MySQL（MVP）；V2+ 演进 TDengine。
- MVP 数据表设计（MySQL）：
  ```
  设备遥测表 device_telemetry: (id, device_id, property_key, value, ts)
  按 device_id 建索引 + 时间分区；V2+ 迁 TDengine 超级表/子表
  ```
- MVP 用 MySQL 分区表 + 定时归档；V2+ 用 TDengine 原生 TTL/降采样/聚合。

**② 设备日志存储**

- 上下线日志、操作记录、指令下发记录 → MySQL 或 ES。
- 支持按设备、时间范围检索，用于问题追溯。

**③ 规则引擎**

- 可视化配置规则：`触发条件（属性值/事件）→ 动作（转发/入库/告警）`。
- 支持的动作类型：
  - HTTP 推送（Webhook 到应用）
  - MQTT 转发（跨主题转发）
  - 数据库写入（MySQL）
  - 告警触发（联动告警引擎）
- MVP 用 EMQX Rule Engine + 自研规则服务，复杂场景后续可接入 Flink。

**④ 数据订阅与推送**

- WebSocket 实时推送：应用订阅设备 Topic，实时接收属性/事件数据。
- 支持按设备、按分组、按产品订阅，服务端主动推送。

> **MVP 落地说明**：MVP 阶段不引入 WebSocket，控制台实时数据走 **HTTP 轮询**（前端每 3~5s 调 REST API 拉最新数据）；WebSocket 实时订阅 V2 补齐（见决策记录 #8）。

### 5.1 性能

| 指标           | 目标                     | 说明                |
| ------------ | ---------------------- | ----------------- |
| 单节点 MQTT 连接数 | ≥ 10 万                 | EMQX 单节点能力，集群水平扩展 |

| 规则引擎延迟       | < 100ms                | 触发到动作执行           |

### 5.2 可用性

- **99.9% SLA**：月故障时长 < 43.2 分钟。
- **故障转移**：EMQX 集群、微服务多副本、数据库主从切换，无单点。
- **数据备份**：关系库/时序库定时备份，支持异地容灾。

### 5.3 安全性

- **传输加密**：设备接入全链路 TLS（MQTT over TLS，端口 8883）。
- **设备身份认证**：一机一密/一型一密/Token，密钥加密存储，支持设备端证书（X.509）。
- **数据隔离**：多租户逻辑隔离 + 数据加密，防止越权访问。
- **防重放攻击**：消息携带时间戳 + 随机数（nonce），服务端校验防重放。
- **API 安全**：JWT + API Key + 限流 + IP 白名单，敏感操作二次验证。

### 5.4 扩展性

- **水平扩展**：接入层（EMQX 集群）、平台层（微服务多副本）、数据层（Kafka/TDengine 集群）均可横向扩展。
- **协议插件化**：新增协议通过插件机制接入，不改核心代码。
- **功能模块化**：微服务拆分，模块独立部署、独立升级。

### 5.5 兼容性

- 支持主流嵌入式平台：STM32（裸机/FreeRTOS）、ESP32（ESP-IDF/Arduino）、Linux（OpenWrt/树莓派）。
- SDK 支持：MQTT 3.1.1 / 5.0，TLS 1.2+，C/Python/Java/Node.js。
- 浏览器兼容：控制台支持 Chrome/Edge/Safari 最新两个版本。

## 7. 技术风险与难点

### 7.1 海量并发连接处理

| 方案        | 说明                                    | 结论       |
| --------- | ------------------------------------- | -------- |
| **EMQX**  | Erlang/OTP，单节点百万级连接，内置规则引擎/数据桥接，企业级成熟 | ✅ **首选** |
| VerneMQ   | Erlang，分布式设计好，但社区活跃度、文档弱于 EMQX        | 备选       |
| Mosquitto | C 语言，轻量，适合单机/开发调试，集群能力弱               | 仅开发调试    |

**决策**：MVP 用 EMQX 开源版；企业版作为可选付费增值（V2 后视客户规模评估）。

### 7.2 数据上报 HTTP 推送模式的性能与可靠性（MVP 关键风险）

- **风险**：MVP 采用 EMQX Webhook 把设备报文 HTTP 推送给 Java 服务，是"先跑通"的捷径，但存在两个隐患——① 设备高频上报时，EMQX→Java 的 HTTP 调用链成为吞吐瓶颈（每条报文一次 HTTP 往返）；② Java 服务宕机或响应慢时，消息可能积压甚至丢失。
- **应对**：① EMQX Webhook 开启批量发送与本地重试；② Java 侧异步接收 + 线程池 + 有界队列缓冲，削峰填谷；③ 数据量大（> 万级 msg/s）后，V2 演进为 EMQX 规则引擎 → Kafka（可回放、可堆积），Java 消费 Kafka，彻底解耦；④ 关键上报加 QoS=1，保证至少一次投递。

### 7.3 时序数据存储（MVP 用 MySQL → V2 演进 TDengine）

| 方案           | 优势                             | 劣势                      | 结论        |
| ------------ | ------------------------------ | ----------------------- | --------- |
| **TDengine** | 写入快、压缩比高（~10:1）、SQL 友好、集群开源（V2+ 采用） | 生态较 InfluxDB 小          | ✅ **首选**  |
| InfluxDB     | 生态广、TICK 栈完整                   | 2.x 集群闭源、查询语言 Flux 学习成本 | 备选        |
| TimescaleDB  | PG 扩展、SQL 兼容极好、适合复杂查询          | 写入性能弱于 TDengine、压缩比一般   | 团队熟 PG 可选 |

**MVP 决策**：时序数据 MVP 存 MySQL（数据量小、先跑通）；V2+ 当单设备秒级上报、数据超千万条时迁移 TDengine（超级表/子表 + 合理 TTL + 降采样预聚合）。

### 7.4 设备鉴权接口的并发性能（连接风暴）

- **风险**：MVP 用 EMQX HTTP 认证插件，设备每次连接 EMQX 都同步调用 SpringBoot 鉴权接口。设备批量上电、断网重连时会出现"连接风暴"，鉴权接口被打爆，拖垮整个后端。
- **应对**：① 鉴权接口极简（只查 Redis 缓存的 device_key，不落库）；② 鉴权结果在 EMQX 侧缓存（EMQX 支持认证结果缓存 TTL）；③ 鉴权接口独立限流与快速失败；④ 设备侧加随机退避重连（抖动 jitter），避免雪崩。

### 7.5 规则引擎性能与可靠性

- **风险**：规则复杂后成为瓶颈，规则引擎故障影响数据流转。
- **应对**：MVP 不引入独立规则引擎，用 EMQX Rule Engine（Webhook 转发）+ Java 内业务逻辑实现简单联动；V2+ 再上自研规则服务，复杂流式处理后期引入 Flink。

### 7.6 多租户数据隔离

- **风险**：多租户数据越权、资源争抢（V2 引入多级租户后成为重点）。
- **应对**：MVP 单租户多项目，所有查询强制带 project_id 条件；V2 引入组织→项目→资源三级隔离 + 中间件拦截 + 敏感数据加密 + 租户资源配额限流。

### 7.7 设备端 SDK 兼容性

- **风险**：C SDK 要兼容裸机/FreeRTOS/ESP32/Linux 多种环境，RAM/ROM 差异大。
- **应对**：C SDK 采用分层设计（平台抽象层 HAL + 核心协议层），条件编译适配；基于成熟库（paho/esp-mqtt）封装；提供完整移植文档与示例。

### 7.8 其他风险

- **指令可靠性**：控制指令丢包/超时。**应对**：指令幂等 + 状态追踪 + 离线缓存 + 超时重试。
- **OTA 安全性**：固件被篡改。**应对**：MD5 + 签名校验 + HTTPS 下载。
