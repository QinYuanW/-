## 0. 战略判断（先看这个，再动手）

### 0.1 目标变了，打法必须变

MVP 阶段的目标是"**证明这条路走得通**"，V2 的目标是"**证明你懂为什么这么走**"。
面试时真正值钱的不是"我用了 Kafka/TDengine"，而是——**你怎么发现需要它们，以及迁移前后的数据对比**。

### 0.2 三条铁律（违反会做无用功）

| # | 铁律 | 违反后果 |
|---|------|---------|
| 1 | **先建可观测，再做优化** | 没监控做性能优化 = 闭眼调参，面试一问"瓶颈在哪"就露馅 |
| 2 | **先造数据打到真瓶颈，再上架构** | 324 msg/s 的数据量去论证需要 Kafka，一句"你 MySQL 到瓶颈了吗"就被问穿 |
| 3 | **每个架构决策留一份对比报告** | 没有前后数据，"为什么选 TDengine" 就只是技术堆砌 |

### 0.3 对需求文档 §8.2 排期的两处调整

需求文档原排期：V2 = OTA/仪表盘/告警/OpenAPI；V3 = 运维监控/CoAP·Modbus/压测调优。
**本清单调整如下，理由写在对应阶段下：**

1. **运维监控从 V3 提前到 V2-B** —— 它是后续所有优化的前提设施，越早建越省事。
2. **新增 V2-C 规模化压测阶段** —— 原排期把压测放在 V3 收尾，但压测应该是"架构演进的立项依据"，必须前置到引入 Kafka/TDengine 之前。

### 0.4 明确暂缓 / 降级的能力（范围声明）

需求文档 §8.2 原排期中的部分能力**不在 V2 主线范围内**（有意 descope，避免与"生产级演进"主线抢时间），面试 / 答辩需能说清"为什么暂缓"：

| 能力 | 需求文档出处 | 去向 |
|------|------------|------|
| OpenAPI 对外 | §4.9 | 暂缓：V2 以控制台 + 内部 REST 为主，对外开放 API 留长期 |
| 可视化仪表盘（拖拽式产品盘） | §4.6 | 暂缓：V2 仅做 Grafana 运维大盘（B3），产品级自定义盘留长期 |
| 业务级告警通知（阈值→推送钉钉/飞书/短信） | §4.7 | 暂缓：V2 仅做规则联动（E3）+ 运维告警（B6），不接面向用户的通知 |
| RBAC 角色权限（管理员/开发者/观察者） | §4.8 | 暂缓：V2 仅做多租户隔离（F4），细粒度角色权限留长期 |
| CoAP / Modbus / TCP 多协议 | §4.1 / §8.2 | 暂缓：V2 保持 MQTT 单协议，多协议留长期 |

## 三、阶段 V2-C · 规模化压测（2~3 周）⚠️ 新增阶段

> 目标：**主动把系统打到瓶颈**，产出两份报告——《MySQL 时序瓶颈分析》与《Webhook 直推可靠性边界》。
> **为什么新增**：这两份报告是 D 阶段两项演进的立项依据——C4 支撑 TDengine（需求 §7.3），C5 支撑 Kafka（需求 §7.2）。没有它们，架构演进在面试中站不住。

| # | 任务 | 完成标志 | 状态 |
|---|------|---------|------|
| C1 | 万级设备模拟脚本 | 可模拟 1000~10000 台设备持续上报（改造 `test_storm_telemetry.py`） | ✅ |
| C2 | 打到 MySQL 真实写入瓶颈 | 出现明确拐点：入库 RT 陡增 或 写入失败 | 🔄 |
| C3 | 定位 MySQL 瓶颈根因 | 出具结论：索引？写入放大？连接池？磁盘 IO？ | ✅ |
| C4 | 输出《MySQL 时序瓶颈分析报告》 | 含基线数据、拐点数据、根因分析（对应需求 §7.3） | ✅ |
| C5 | 论证「Webhook 直推 vs Kafka」边界 | 复现直推丢消息：队列打满 / 后端重启丢在途 / EMQX 重试失效，对应需求 §7.2 | ✅ |

> 📌 **已知坑预警**：压测前务必先确认磁盘 IO 与杀毒白名单（历史出现过 D 盘 page_cleaner 卡顿拖垮 MySQL 的风险），否则会误判瓶颈在 MySQL。
> 📌 **C5 面试价值**：压出「进程内队列丢消息」的那一刻，就是「为什么需要 Kafka」的唯一实证——MVP 的 BUG-7（`RejectedExecutionException`）已是苗头。

## 四、阶段 V2-D · 数据链路演进（4~5 周）

> 目标：用 Kafka 解耦数据流转，用 TDengine 承载时序数据。
> **前置依赖**：C4（MySQL 时序瓶颈）＋ C5（Webhook 直推可靠性边界）两份报告必须完成，分别支撑 TDengine 与 Kafka

| # | 任务 | 完成标志 | 状态 |
|---|------|---------|------|
| D1 | Kafka 接入 | 前置：C5 报告证明直推丢消息；EMQX 规则 → Kafka → Java 消费者组，替代 Webhook 直推 | ⬜ |
| D2 | 消费端幂等 + 背压 | 重复消费不产生脏数据；消费不过来时不丢消息 | ⬜ |
| D3 | TDengine 迁移 | 超级表/子表设计落地，历史数据双写灰度 | ⬜ |
| D4 | 一致性校验 | 双写期间 MySQL 与 TDengine 数据比对无差异 | ⬜ |
| D5 | 迁移前后性能对比报告 | **本阶段最核心产出**，含写入吞吐、压缩比、查询 RT 三组对比 | ⬜ |

> 📌 **D5 是简历上的硬通货**：`MySQL 971 行/s → TDengine XXXX 行/s，压缩比 X:1` 这种带数字的对比，比任何技术名词都有力。

## 九、V2 依赖关系（关键路径）

```
A 封板 ──► B 可观测 ──► C 规模化压测 ──► D 数据链路演进 ──► G 规模化部署
                  │                                              ▲
                  └──────► E 平台核心能力 ──► F OTA与安全 ────────┘
                                    │
论文支线 ◄─────────────────────────┘（G 阶段压测完成后用真实数据反哺）
```

**关键路径说明**：
- **B → C → D 是不可跳跃的**：跳过 C 直接做 D，架构演进就失去了 C4/C5 的立项依据。
- **E 可与 D 并行**：平台能力不依赖数据链路，两者可穿插推进。
- **F1（OTA）依赖 E1（设备影子）**：OTA 状态同步需要影子做载体。
