## 0. 战略判断（先看这个，再动手）

### 0.1 目标变了，打法必须变

MVP 阶段的目标是"**证明这条路走得通**"，V2 的目标是"**证明你懂为什么这么走**"。
面试时真正值钱的不是"我用了 Kafka/TDengine"，而是——**你怎么发现需要它们，以及迁移前后的数据对比**。

### 0.2 三条铁律（违反会做无用功）

| # | 铁律 | 违反后果 |
|---|------|---------|
| 1 | **先建可观测，再做优化** | 没监控做性能优化 = 闭眼调参，面试一问"瓶颈在哪"就露馅 |
| 2 | **先造数据打到真瓶颈，再上架构** | 324 msg/s 的数据量去论证需要 Kafka，一句"你 MySQL 到瓶颈了吗"就被问穿 |
| 3 | **每个架构决策留一份对比报告** | 没有前后数据，"为什么选 TDengine" 就只是技术堆砌 |

### 0.3 对需求文档 §8.2 排期的两处调整

需求文档原排期：V2 = OTA/仪表盘/告警/OpenAPI；V3 = 运维监控/CoAP·Modbus/压测调优。
**本清单调整如下，理由写在对应阶段下：**

1. **运维监控从 V3 提前到 V2-B** —— 它是后续所有优化的前提设施，越早建越省事。
2. **新增 V2-C 规模化压测阶段** —— 原排期把压测放在 V3 收尾，但压测应该是"架构演进的立项依据"，必须前置到引入 Kafka/TDengine 之前。

### 0.4 明确暂缓 / 降级的能力（范围声明）

需求文档 §8.2 原排期中的部分能力**不在 V2 主线范围内**（有意 descope，避免与"生产级演进"主线抢时间），面试 / 答辩需能说清"为什么暂缓"：

| 能力 | 需求文档出处 | 去向 |
|------|------------|------|
| OpenAPI 对外 | §4.9 | 暂缓：V2 以控制台 + 内部 REST 为主，对外开放 API 留长期 |
| 可视化仪表盘（拖拽式产品盘） | §4.6 | 暂缓：V2 仅做 Grafana 运维大盘（B3），产品级自定义盘留长期 |
| 业务级告警通知（阈值→推送钉钉/飞书/短信） | §4.7 | 暂缓：V2 仅做规则联动（E3）+ 运维告警（B6），不接面向用户的通知 |
| RBAC 角色权限（管理员/开发者/观察者） | §4.8 | 暂缓：V2 仅做多租户隔离（F4），细粒度角色权限留长期 |
| CoAP / Modbus / TCP 多协议 | §4.1 / §8.2 | 暂缓：V2 保持 MQTT 单协议，多协议留长期 |

### D1/D2 验证记录（2026-09-11）

**D1 Kafka 链路**：`docker-compose.yml` 加单节点 Kafka 3.9.0（KRaft 双 listener）；链路设计见 `docs/02_设计契约/EMQX配置方案.md`；代码 `config/KafkaConfig`（acks=all + 容器托管 ack）+ `listener/TelemetryKafkaListener`，topic `iot.telemetry`。
**崩溃恢复实测（BUG-18）**：QoS0 突发 20000 条 → `taskkill` 后端 → 重启后 DB 靠 Kafka 持久化副本续涨到 9202，`LAG=0` 消费者追平 → **「后端重启丢在途」已解决**；残余边界：EMQX→后端 webhook 仍是尽力而为 HTTP，后端宕机 > `request_ttl(45s)` 期间突发仍会在 EMQX 侧过期丢弃（dropped.expired=10798）。
**D2 幂等（BUG-19 / BUG-20）**：唯一键 `uk_device_prop_val_ts (device_id, property_key, value, ts)`；`insertBatch` 加 `ON DUPLICATE KEY UPDATE id=id`。BUG-20 修正了仅含 `(device_id,property_key,ts)` 时 QoS0 同毫秒 ts 误折叠不同上报（丢 ~90%）——加 value 后突发 5000 条 **distinct=5000 零丢失**，真重放仍正确去重。
**D2 背压（BUG-21，实验驱动）**：先做 ack 语义实验（`docs/05_压测报告/D2-2_消费端ack语义实验报告.md`）——实测 partition 2 的 `CURRENT-OFFSET` 从 2 **直接跳到 4**，证明 `AckMode.MANUAL` 下失败记录会被后一条成功 ack **越过提交**，静默丢失（无重试、无死信，失败计数恒 1.0）。据此实施：`@RetryableTopic` 非阻塞重试阶梯（`-retry-0/1/2`，退避 1→2→4s）+ `iot.telemetry-dlt` 死信 + `PermanentTelemetryException` 分类（永久失败跳过重试）。
附带后果：**`AckMode.MANUAL` 被撤掉**（`@RetryableTopic` 不支持手动 ack，且它正是本 bug 成因），「消费成功才确认」改由「容器托管提交 + 重试/死信 + D2-1 唯一键幂等」共同兑现。
**运行验证（2026-09-11 19:48–19:51，三项全绿）**：① 永久失败（未注册 `ghost_perm_001`）→ `failures{permanent}=1`、`dlt_total=1`，`retry-0/1/2` 位点仍 0（跳级直达 DLT）；② 瞬时失败（超长 value 触发 MySQL 1406）→ `failures{retryable}=4`（=`attempts=4`），消息流经 `retry-0→1→2` 后落 dlt；③ 复刻案发现场（同 key 先失败后成功）→ 成功消息**入库 1 行** 且 失败消息**完整留存 DLT**（`dlt_total=3`），**零丢失**。详见实验报告 §8。

> 📌 **D5 是简历上的硬通货**：`MySQL 971 行/s → TDengine XXXX 行/s，压缩比 X:1` 这种带数字的对比，比任何技术名词都有力。

**设计取舍：WS 为主 + 轮询兜底**
WS 连通即停轮询；WS 断开立刻恢复轮询（`ws.js` 后台指数退避 1→2→4→8s 重连，上限 10s）。
好处：**不会出现"推送一挂页面就死"**，同时优化效果能被实测量化。

**两个实现约束（已写进 `TelemetryWebSocketHandler` 类注释）**
1. **会话表是实例内存态 → 仅适用单实例部署**；多副本需改 Redis Pub/Sub 或 STOMP broker 中转 → **记入 V2-G（平台多副本）前置条件**。
2. **`WebSocketSession` 非线程安全**：并发 `sendMessage` 会抛 `IllegalStateException(TEXT_PARTIAL_WRITING)`，**多个 Kafka 消费线程同时广播必然触发** → 发送处已加 `synchronized (session)`。

**新增依赖**：`spring-boot-starter-websocket`（`tomcat-embed-websocket` 已随 starter-web 传递引入，但注册端点所需的 `WebSocketConfigurer` 在 `spring-websocket` 模块中，必须显式引 starter）。

## 九、V2 依赖关系（关键路径）

```
A 封板 ──► B 可观测 ──► C 规模化压测 ──► D 数据链路演进 ──► G 规模化部署
                  │                                              ▲
                  └──────► E 平台核心能力 ──► F OTA与安全 ────────┘
                                    │
论文支线 ◄─────────────────────────┘（G 阶段压测完成后用真实数据反哺）
```

**关键路径说明**：
- **B → C → D 是不可跳跃的**：跳过 C 直接做 D，架构演进就失去了 C4/C5 的立项依据。
- **E 可与 D 并行**：平台能力不依赖数据链路，两者可穿插推进。
- **F1（OTA）依赖 E1（设备影子）**：OTA 状态同步需要影子做载体。
- **E3（规则引擎）依赖 E5（产品与物模型管理）**：规则要「按物模型属性配阈值告警」，没有 E5 只能对写死的属性生效 → **E5 须先于 E3**（编号是补录顺序，不代表排期顺序）。
- **D 的排期（2026-09-11 决策 · 阿枢建议，汤园采纳）**：D3-D5 **不垫底，错峰排在 E1→E2 之后、F/G 之前**。理由：
  ① C4/C5 已固化成文档，「B→C→D 不可跳跃」的立意（给 D 攒立项依据）**已履行完毕**，D 何时做不影响依据成立；

  ③ D 的唯一硬依赖是 **G3/G4**（全链路压测定稿、架构演进文档要 D5 的数据）→ 只需保证 **D 早于 G3/G4**。
  > 期间的 D3 评审报告与 P0-1 待决项**保留原样**，回来接着做即可，不需重做分析。
- **E6 的排期（2026-09-13 决策 · 阿枢建议）**：新增的「控制台统计接口」（详见 **§十一**）排在 **E2 之后、E3 之前**，且**必须早于 D3**。理由：D5 报告要求「写入吞吐 / 压缩比 / **查询 RT**」三组对比，写入吞吐由 C4 提供、压缩比由 D3 自测，**而「查询 RT」目前没有任何基线**——E6 的 `COUNT(*)` 与按月聚合正是查询侧最典型负载，先做 MySQL 版才有得比。**这条把 D 的排期从「E1→E2 之后」顺延为「E3 之后」，仍早于 F/G，不违背原决策初衷。**

### 11.3 为什么 E6 必须排在 D3（TDengine）之前 ← 本次排期的核心结论

D5 报告的定义是「含**写入吞吐、压缩比、查询 RT** 三组对比」：

| 对比维度 | 素材来源 | 现状 |
|---------|---------|------|
| 写入吞吐 | C4 报告 + C2 收尾实测 | ✅ **D5 用基线已定**（09-15）：**优化后 13.6ms/条、169 msg/s（≈507 行/s）** —— 拿"最强状态的 MySQL"去对 TDengine |
| 压缩比 | D3 迁移时自测 | ⏳ D3 产出 |
| **查询 RT** | **？** | 🔴 **没有任何基线** |

**E6a（`COUNT(*)`）与 E6b（按月 `GROUP BY`）正是查询侧最典型的两类负载**——全表/大范围扫描，且是仪表盘每次打开都要跑的查询。先做 MySQL 版拿到 RT，D3 迁移后才有得比。

> ⚠️ **若把 E6 排到 D3 之后**，D5 报告就只剩「写入吞吐 + 压缩比」两条腿，而查询侧永远缺基线——**这正是铁律 3「每个架构决策留一份对比报告」要防的情况**。
