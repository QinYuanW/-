## 一、改写逻辑（为什么同一项目要换叙事）

| 证据形式 | 架构决策、性能数字、协议语义 | **部署步骤、配置项、排查路径、排查记录、交付文档** |
| 技术深度展示点 | 幂等键设计、重试阶梯、DLT | **中间件配置、端口与网络寻址、数据卷持久化、证书、数据库运维** |
| 最有价值素材 | 2.5× 优化、用数据否决迁移 | **31 条故障排查记录、四层排查路径、配置静默回退排查** |

## 二、定稿（6 条）

**物联网 PaaS 云平台** · 独立开发 · 部署实施 · 2025.06 – 2025.09

独立完成一套物联网 PaaS 平台的本地化部署与交付：覆盖多组件环境搭建、中间件配置、数据初始化、真机联调验收与故障排查，并沉淀可交接的文档集。

- **环境部署与容器编排**：完成平台全栈环境部署 —— MySQL 5.7 独立安装在宿主机（数据目录、连接池参数、专用账号与访问权限配置），EMQX / Redis / Kafka / Prometheus / Grafana / Alertmanager 六组件以 Docker Compose 编排；处理容器与宿主机的双向寻址（容器访问宿主用 `host.docker.internal`、宿主访问容器用 `localhost`）、端口映射与数据卷持久化。

- **中间件配置与调通**：配置 EMQX 设备认证器（HTTP 回调）与数据转发链路（连接器 + 动作 + 规则三层，缺一不可），并以 API Key 引导文件方式解决 Dashboard 账号无法调用管理 API 的问题；在容器内生成带 SAN 的自签证书启用 MQTT over TLS（8883），用**目录挂载**替代文件拷贝，避免容器重建后证书静默回退为无效默认证书；配置 Kafka 单节点 KRaft 模式及消费参数。

- **数据初始化与迁移**：维护 11 张核心表（遥测数据按月分区）；将 3 份互相冲突的建表脚本收敛为**单一权威源**，并通过逐表比对（11 表 / 102 列 / 52 索引 / 13 分区零差异）确保脚本可从零复现真实库结构；为真实库补齐 113 条字段注释（执行前后结构快照逐行一致）；排查并修复容器重建导致 Grafana 密码与自建大盘丢失的问题（补挂数据卷并实测验证）。

- **联调与验收**：完成 ESP32 真机端到端接入验证 —— 设备三元组鉴权 → 遥测上报入库 → 平台指令下发 → 设备 ACK 状态回传全链路打通；对照接口契约逐条核验 40+ 个接口（11 个控制器）的出入参格式；建立"**逐面板出数**"的验收标准，对监控大屏 18 个面板逐条核验，修复其中 4 块"面板存在但永远无数据"的伪正常状态。

- **故障排查与响应**：沉淀 **31 条故障排查记录**（现象 / 复现步骤 / 根因 / 处置结果）；建立四层递进排查路径（业务接口 → 健康检查 → 数据库直连 → 容器状态）并固化快速判据 —— 例如"接口请求耗时约 30 秒即为数据库连接异常"，避免在中间件上空耗时间；独立定位配置静默回退、缓存失效导致"改了不生效"、服务状态显示与端口监听不一致等现场问题。

- **文档与交付**：输出可交接文档集 —— 接口契约、端口与访问清单、设备接入验证流程、三份压测报告与缺陷复盘日志，使整套环境具备**他人可复现、可接手**的条件。

## 五、实施岗高频追问预案

1. **"容器重建后配置丢了，你怎么查出来、怎么根治？"**
   → **症状是"静默回退"**：EMQX 证书退回自带的无效默认证书（设备全连不上却无报错）、Grafana 密码与自建大盘归零回 admin/admin。
   → 根因：用 `docker cp` 拷进容器的文件在容器重建时被清空；容器自身写入的状态没挂数据卷。
   → 根治：**给容器的配置一律走目录挂载（bind mount）；容器持久化的状态必须挂卷。**
   → ⚠️ 关键认知：**"资源存在"不等于"功能可用"** —— 不能拿"大盘还在"当"数据还在"的证据。

2. **"客户说系统访问不了 / 很慢，你的排查顺序？"**
   → 四层递进：**业务接口 → 健康检查 → 数据库直连 → 容器状态**。
   → 固化判据：**接口请求耗时约 30 秒 = 数据库连不上**（一眼定方向，不必在 EMQX / Redis 上绕）。
   → 反例警惕：**服务状态会骗人** —— 服务管理工具显示 Running，实际可能端口无监听；决定性证据是**端口监听检查 + 客户端直连报错码**。

3. **"TLS 证书是怎么配的？为什么用自签？"**
   → 容器内用 OpenSSL 生成**带 SAN** 的自签证书（SAN 含 localhost / 127.0.0.1 / 局域网 IP），替换 EMQX 自带的无 SAN 默认证书（无 SAN 会导致设备侧校验失败）；服务端启用 8883 单向 TLS，证书目录纳入版本管理并挂载进容器。
   → ⚠️ 附带一个协议细节：认证回调的**拒绝响应必须返回 `application/json`**，否则 EMQX 会持续报解析失败 —— 这类"服务端刷错误但功能看着正常"的问题，实施现场很常见。

4. **"数据库连不上你怎么处理？"**
   → 先确认监听（端口检查）再确认服务、最后用客户端直连复现并看错误码；账号需同时存在 `'用户'@'%'` 与 `'用户'@'localhost'` 两条授权；连接池参数（连接超时 / 最大存活时间）要短于数据库的 `wait_timeout`，否则会拿到已断开的连接。

5. **"你怎么保证交付后别人能接手这套环境？"**
   → 三件事：**建表脚本收敛为单一权威源**（此前 3 份互相冲突，单跑任何一份都建不出可用库）；**输出端口与访问清单、验证流程**；**验收标准可执行**（如监控大屏要求"逐面板出数"而不是"能打开"）。

6. **"实施岗你可能要写脚本，你会吗？"**
   → 项目中的建表、结构校验、批量验证与压测脚本均由 PowerShell / Node 自行编写；同时对 Windows 环境下的常见坑（脚本行尾、控制台引号吞字符、编码）有实际处置经验。
