## 一、定稿（7 条）

**物联网 PaaS 云平台** · 独立全栈开发 · 2025.06 – 2025.09

独立完成一套面向设备的物联网 PaaS 平台（对标 OneNET）：覆盖设备接入鉴权、高可靠遥测链路、物模型驱动的前端控制台与可观测体系，并以压测数据驱动容量治理。

- **设备接入与指令闭环**：以 EMQX 三元组鉴权 + Spring Boot 认证回调打通 MQTT 上下行链路，落地指令状态机（待下发 → 已下发 → 已执行/失败/超时，超时由定时扫描兜底）与 ACK 幂等（重复、乱序回报不覆盖终态）；将设备/产品启停统一收敛到认证、遥测、事件、指令四条入站链路，实现停用后即时拒绝接入。固件侧基于 ESP32-S3 同步完成定时上报与下行指令执行。

- **遥测链路重构：从"打满即丢"到零丢失**：原进程内队列直推在压测中打满即**静默丢弃**（交付率跌至 30%，且应用侧指标全绿、故障不可见），改为 EMQX → Kafka → 消费者组解耦；以幂等唯一键 + 冲突吞并实现 at-least-once 下的写入去重，用失败分级 + 非阻塞重试阶梯（1→2→4s）+ 死信队列根治"失败记录被后续提交越过"的静默丢失。实测：**突发 5000 条零丢失、进程强杀重启后零丢失。**

- **压测定位真瓶颈，用数据否决一次架构迁移**：搭建压测与指标观测体系主动把系统打到瓶颈 —— 先修复应用侧写入路径（禁用控制台 SQL 日志、单行 INSERT 改批量、热点行更新改时间窗聚合），稳态吞吐提升 **2.5×（约 98 → 248 msg/s）**；再以链路耗时埋点、线程栈与 InnoDB 状态指标证明瓶颈在**消费侧处理链路**而非数据库（单条 13.6 ms，DB 侧几乎空闲：`Threads_running=2`、`log_waits=0`），据此判断引入时序库"收益不抵复杂度"并终止迁移。

- **数据模型与安全加固**：设计 11 张核心表的数据模型，遥测数据按月分区存储；设备密钥以 **AES-256-GCM** 密文入库（旧明文首次认证自动转密、零停机迁移），MQTT 接入启用 **TLS（8883）**（自签带 SAN 证书 + 容器持久化挂载）；将建表脚本收敛为单一权威源，并逐表比对保证脚本可复现真实库结构。

- **前端控制台（物模型驱动）**：以 Vue 3 + Vite 构建控制台，页面与控件 **100% 由物模型（TSL）驱动** —— 属性按读写权限自动分流为数据卡片 / 控制控件 / 服务按钮；新增传感器只需编辑物模型，**前后端渲染代码零改动**。实时数据由 5s 轮询改为 WebSocket 推送，端到端延迟 **2.5s → 22ms**（12 秒内轮询请求降至 0 次），并保留轮询兜底与指数退避重连。

- **可观测体系**：以 Docker Compose 编排 EMQX / Kafka / Redis / Prometheus / Grafana / Alertmanager 六服务链路（MySQL 独立部署于宿主机）；以 Micrometer 自定义埋点（链路耗时 P50/P95/P99、队列水位、丢弃计数）接入 Prometheus + Grafana（18 面板），并通过逐面板数据体检修复 4 块"面板存在但永远无数据"的伪正常状态 —— 把监控验收标准从"能看到大盘"推进到"每块面板都能出数"。

- **核心成果**：独立完成设备固件 → 云平台 → 控制台的全链路开发，沉淀 **31 条缺陷复盘**（含静默丢数据、缓存失效边界等 Blocker 级问题）与 API 契约、三份压测报告等可复现工程文档；并从修复过程中归纳出"资源存在 ≠ 功能可用""回执正常 ≠ 改动生效"等验收准则。

## 五、高频追问预案（每条都要能讲出"为什么这么设计"）

1. **"Kafka 用了 at-least-once，怎么保证不重复？"**
   → 不追求 exactly-once（成本高），改在写入侧做幂等：唯一键 `(device_id, property_key, value, ts)` + `ON DUPLICATE KEY UPDATE id=id`。
   ⚠️ 反直觉点值得讲：唯一键最初**不含 value**，结果 QoS0 同毫秒突发时不同上报被误折叠，静默丢 ~90% —— **幂等键必须包含"业务上区分两条上报"的全部维度**，不能只看时间戳。

2. **"你怎么知道瓶颈不在数据库？"**
   → 三条独立证据：① 耗时埋点显示单条 13.6 ms，MySQL 写入只占 5~8 ms；② 压测中 DB 侧 `Threads_running=2`、`log_waits=0`，几乎空闲；③ 应用侧队列零积压、零丢弃，但 Kafka lag 达 2 万+ → 瓶颈在消费线程而非下游。
   ⚠️ 方法论彩蛋：压测时**不要边压边做重量级观测**（曾因边压测边跑观测脚本，把单条耗时从 13.6 ms 抬到 16.1 ms —— 观测者效应）。

3. **"为什么最后没换 TDengine？"**
   → 换库只能压掉写入侧一半开销，剩下一半仍在消费链路；当时数据量下压缩比/自动过期非刚性需求 → 引入第二套存储不划算。**"知道不做什么"和"做了什么"同样是工程判断。**

4. **"WebSocket 有什么坑？"**
   → ① 会话表是实例内存态，只适用单实例，多副本需改 Redis Pub/Sub；② `WebSocketSession` 非线程安全，多个消费线程并发广播会抛 `TEXT_PARTIAL_WRITING` → 发送处加 `synchronized (session)`。

5. **"这个平台最像生产系统的设计是哪个？"**
   → 设备影子 + "命令 vs 期望值"的语义分家：命令离线即失败并提示，期望值离线挂起、上线自动补发。这条是实测 UI 后主动修正的 —— 原实现让离线命令挂起等上线执行，等于让**过期上下文被延迟执行**（对照 OneNET / AWS Device Shadow 后收敛语义）。
