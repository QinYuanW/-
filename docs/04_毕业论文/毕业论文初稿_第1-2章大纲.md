## 第 1 章　绪论

### 1.1 研究背景与意义

- **【写什么】** 物联网规模化落地的三大痛点 → 本课题价值
- **【素材】** 需求文档 §1.1
- **【怎么写】** 三段递进：
  1. **行业趋势**：物联网从"单点试点"走向"规模化落地"，设备接入量爆发；
  2. **三大痛点**：设备碎片化（芯片/模组/协议千差万别）→ 协议不统一（物模型缺失，同一字段叫法各异）→ 开发周期长（自建方案动辄 3~6 个月）；
  3. **本课题意义**：现有大厂平台生态绑定、私有化成本高，OneNET 定制能力有限，留出"轻量、可私有化、低成本"的自研空间。
- **【学术化示例】** 产品文档写"设备接入云平台这一环是行业最大的效率黑洞" → 论文写"设备接入环节的碎片化问题已成为制约物联网应用规模化落地的关键瓶颈"。

### 1.2 国内外研究现状

- **【写什么】** 国外平台 → 国内平台 → 现有方案不足
- **【素材】** 需求文档 §6 竞品分析
- **【怎么写】** 三层结构：
  1. **国外**：AWS IoT Core、Azure IoT Hub 的成熟能力与高门槛；
  2. **国内**：阿里云 IoT（物模型最强）、腾讯云 IoT、华为云 IoT、OneNET（轻量但定制弱）；
  3. **不足归纳**：大厂平台"生态绑定 + 私有化成本高 + 对中小团队重"，运营商系平台"定制能力有限、数据不出内网受限"。
- **【答辩高频点】** 老师必问"你和 OneNET 比，创新点在哪"——标准答案：**私有化原生支持 + 生态中立 + 物模型 TSL 贯穿全链路**（这三点就是论文第 3 章要重点展开的亮点）。

### 1.3 本文主要工作与组织结构

- **【写什么】** 本文做了什么 + 论文结构
- **【素材】** 需求文档 §1.2 目标、§8.1 MVP 清单
- **【怎么写】** 用"(1)(2)(3)"分条列出主要工作：
  1. 设计三层架构（接入/平台/应用）；
  2. 实现设备接入→鉴权→上报→存储→控制的完整闭环；
  3. 搭建 Web 控制台与 OpenAPI 能力。

## 第 2 章　相关技术与总体设计

### 2.1 相关技术基础

> 每个技术按"是什么 + 为什么选它"两段写，选型论证是本小节灵魂。

- **2.1.1 MQTT 协议**：发布/订阅模型、Topic、QoS（0/1/2）、遗嘱消息、KeepAlive。强调"轻量、低功耗、适合资源受限设备"。
- **2.1.2 EMQX 消息中间件**：认证/授权、规则引擎、数据桥接、REST API。重点写**选型论证**——对比 Mosquitto（轻量但集群弱）、VerneMQ（社区弱于 EMQX），结论"单节点百万级连接 + 内置规则引擎 + 企业级成熟"。
- **2.1.3 物模型 TSL**：属性（Property）/ 服务（Service）/ 事件（Event）三类功能定义。**这是全文最核心的概念**，必须单独讲透，因为第 3 章"物模型贯穿全链路"就建立在这个概念上。
- **2.1.4 后端技术栈**：Java 17 + Spring Boot 3.2（模块化单体）+ MySQL 8.0 + Redis 7.2。选型理由见 2.3.3。

### 2.2 系统需求分析

- **2.2.1 功能需求**：设备接入、设备管理（含物模型/设备影子）、数据存储与流转、设备控制、账号权限。
  - 【素材】需求文档 §4
  - 【怎么写】用"用例图 + 功能列表"呈现；标注 P0/P1/P2 优先级体现工程规划能力。
- **2.2.2 非功能需求**：性能、可用性、安全性、扩展性。
  - 【素材】需求文档 §5
  - 【怎么写】必须给**量化指标**：单节点 ≥10 万 MQTT 连接、≥10 万 msg/s、API P99<500ms、99.9% SLA、全链路 TLS。

### 2.3 系统总体设计

- **2.3.1 总体架构**：三层架构图（接入层 EMQX / 平台层 SpringBoot / 应用层 控制台+OpenAPI）。
  - 【素材】需求文档 §3.1
  - 【怎么写】**架构图是本章灵魂**，务必自己重画一张清晰版本；配一段"分层职责"说明。
- **2.3.2 MVP 数据流**：6 步闭环链路图（设备→EMQX→HTTP鉴权→SpringBoot→MySQL/Redis→控制台→REST API下发→设备）。
  - 【素材】需求文档 §3.4
  - 【怎么写】按 6 步编号逐一说明，这张图直接体现"端到端打通"的工程完整性，是加分项。
- **2.3.3 技术选型与理由**：选型对比表。
  - 【素材】需求文档 §3.2
  - 【怎么写】每行给"推荐 + 备选 + 理由"三列；重点是**把决策记录翻译成论证**（见文末对照表）。
- **2.3.4 部署方案**：单机 → MQTT 集群 → 分布式三阶段演进。
  - 【素材】需求文档 §3.3
  - 【怎么写】体现"渐进式演进"的架构思维，呼应非功能需求里的扩展性指标。

## 附 A：产品文档 → 论文语言"翻译对照表"

| 产品文档的写法        | 论文需要的写法                                              |
| -------------- | ---------------------------------------------------- |
| 一个人做微服务太重了     | 针对单租户、中小规模接入场景，采用模块化单体架构降低系统复杂度，通过接口抽象与数据层解耦预留水平扩展能力 |
| MVP 先跑通主干      | 采用渐进式演进策略，分阶段验证核心技术路径                                |
| Webhook 直推简单   | 采用基于 HTTP 回调的消息推送机制，简化接入链路，降低系统耦合                    |
| 先用 MySQL 存时序数据 | MVP 阶段以关系型数据库承载时序数据，验证业务闭环；数据规模增长后迁移至专用时序数据库         |
| Go 留 V2 高并发接入层 | 针对高并发接入场景，预留 Go 语言重写接入层的技术演进空间                       |

> 核心心法：把"工程判断"包装成"设计权衡"。答辩老师要看的是后者。
