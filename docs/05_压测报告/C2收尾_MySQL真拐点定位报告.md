# MySQL 真拐点定位报告（C2 收尾）

> 日期：**2026-09-15** ｜ 关联：C4《MySQL时序瓶颈分析报告》、D3《TDengine迁移方案评审报告》
>
> **结论先行**：**当前瓶颈不在 MySQL，而在消费侧处理链路**。实测单条遥测平均处理 **14.5ms**，其中 MySQL 写入仅占约一半；消费吞吐 **~163 msg/s（489 行/s）**，低于 C4 时代的 248 msg/s —— **回落主因是 E2 WebSocket 广播与 E3 规则引擎同步挂在消费线程上**。
>
> ⚠️ **对 D3 的影响**：换 TDengine **只能解决一半问题**。D3 的价值表述必须从"MySQL 撑不住"改为"**消费链路整体优化中的一环**"。

## 一、本次要闭合的问题

C4 报告结尾留了未闭合项：

> "仍需：① 证明 worker 空闲（thread dump）、② 必要时转向磁盘 IO / InnoDB 参数 / 分区策略排查，再锁定'裸 MySQL 时序插入拐点'精确值，**回填 C2「出现明确拐点」**。"

同时发现**两处口径不一致**：

| 出处 | 消息速率 | 行/s | 性质 |
|---|---:|---:|---|
| 论文 §5 / 任务清单 §11.3 | 324 msg/s | **971** | **短时批次**（1000 条一次性投放，队列吸收后快速排空） |
| C4 报告 | 248 msg/s | **744** | **持续稳态**（分档加压到平台） |

**两者不是一回事**：前者是冲量峰值，后者是持续处理能力。**论文用峰值对标「≥1000 条/秒」的硬指标，严格讲 MVP 阶段未达标。**

## 四、结论

### 4.1 瓶颈定位：消费侧处理链路，MySQL 只占约一半

单条 14.5ms 的构成（按代码路径估算）：

| 环节 | 估算 | 说明 |
|---|---:|---|
| MySQL 批量 INSERT | 5~8 ms | 一次网络往返 + 落盘 |
| **E3 规则引擎** | **~2~3 ms** | **每条上报一次「查规则表」SELECT** + Redis 冷却 `SETNX` |
| **E2 WebSocket 广播** | ~0~2 ms | 有会话时序列化+发送；无会话立即返回 |
| device 在线状态 | ~0 ms（多数） | 5s 窗口聚合，多数命中缓存直接跳过 |
| 框架/反序列化/Kafka | ~3~4 ms | 事务、MyBatis、Jackson 开销 |

> **关键判读**：换 TDengine 能压掉的是最大那一项（5~8ms → 预计 1~2ms），但**剩下一半开销仍在**。

### 4.2 为什么比 C4 时代更慢（248 → 163 msg/s）

**E2/E3 的功能代价**：单条耗时 12.1ms（C4 推算）→ **14.5ms**（本次实测），**增加 2.4ms（+20%）**。

这两件事都**同步跑在消费线程上**，且**当前没有任何指标能看见它们的开销**（只有入口到出口的总耗时）。

> 典型的"功能换性能"，且被 Kafka 的缓冲能力完美掩盖 —— 应用侧指标全绿，实际 58% 数据还躺在 topic 里。

### 4.3 Kafka 的价值被本次实验证实

- 42% 入库率下，**零丢弃、零失败、数据全在**（可随时消费追平）；
- 对比 C4 时代的"打满即丢"（交付率 30% 且静默不可见），**D1 的立项价值获得硬数据背书** ✅

## 五、对 D3 的影响 —— **必须调整价值表述**

| 原表述 | 问题 | 建议新表述 |
|---|---|---|
| "MySQL 撑不住，需要换时序库" | **不成立** —— MySQL 侧几乎空闲（`Threads_running=2`、`log_waits=0`） | "**消费链路整体优化**：时序库替换解决写入侧开销，应用侧异步化解决其余开销" |

**D3 仍然值得做，但理由要换**：

| 理由 | 是否独立成立 |
|---|---|
| 压缩比（10~30:1 vs InnoDB 2~3:1） | ✅ 独立成立 |
| 自动过期/降采样（`KEEP`/`SMA` vs 手写定时任务） | ✅ 独立成立 |
| 聚合查询（列存 vs 全表扫描） | ✅ 独立成立 |
| 写入吞吐 | ⚠️ 有收益（可压掉 5~8ms 的大部分），但**不是"生死问题"** |

> **建议的面试口径**：不要说"MySQL 扛不住所以换 TDengine"，而要说——
> **"压测定位出消费链路是瓶颈，其中 DB 写入占一半开销；换列式时序库把它压下去，同时拿到压缩比与自动过期能力。"**
> 这个说法**每个字都有数据支撑**。

## 六、下一步建议（按优先级）

| # | 动作 | 预期收益 | 成本 |
|---|---|---|---|
| 1 | **规则引擎优化**：规则列表按 `product_key` 缓存（TTL 分钟级），消除每条上报的查库 | 省 ~2ms/条（~15%） | 低 |
| 2 | **消费并发度评估**：确认分区数与并发消费者匹配（3 分区 / 并发 3） | 提升并行度 | 低 |
| 3 | **WS 广播异步化**：广播移出消费线程 | 省 0~2ms 且隔离抖动 | 中 |
| 4 | **D3 TDengine**：按调整后的价值表述推进 | 压掉 DB 侧大部分 + 压缩比 | 高 |
| 5 | 上述优化后**重新压测** | 得到新稳态平台，作为 D5 的 MySQL 侧最终基线 | 低 |

> **口径统一（重要）**：论文 §5 的 971 行/s 是**短时批次**数据。建议改为双口径表述 —— **批次峰值 971 行/s ／ 稳态平台 XXX 行/s**，避免答辩被追问。
