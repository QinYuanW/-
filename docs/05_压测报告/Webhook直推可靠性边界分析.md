# Webhook 直推可靠性边界分析（C5）

> 版本：v1.0 · 日期：2026-09-10
> 定位：**C5 立项报告**——用实测证据论证「EMQX Webhook 直推」在什么条件下丢消息、丢在哪一层，为引入 Kafka 提供不可辩驳的实证。
> 前置成果：《MySQL时序瓶颈分析报告》（C4，docs/05_压测报告/）给出稳态吞吐 ~248 msg/s 的写路径平台，其中应用侧进程内队列在突发时静默丢弃。
> 关联任务：V2-C 阶段 C5「论证 Webhook 直推 vs Kafka」（见《项目任务清单》）。

---

## 0. 一句话结论

**当前链路的可靠性承诺止步于 HTTP 200。** EMQX 的重试/缓冲只覆盖「没拿到 200」的投递；一旦后端返回 200（协议确认），消息离开 EMQX 视野，而进程内异步队列的非持久化导致**协议确认 ≠ 业务落库**——中间隔着一道可丢的、看不见的缝隙。Kafka 的价值正在于把「确认」下沉到持久化层。

---

## 1. 链路现状与论证对象

```
设备 --MQTT(QoS1)--> EMQX --Webhook HTTP--> 后端 Controller(协议入队) --@Async线程池--> MySQL
                        ▲                                          │
                  信封机制(max_retries/                进程内线程池队列(无持久化)
                  inflight/buffer/ttl)                满则静默丢弃(rejected_total)
```

论证对象 = **「EMQX → 后端」这一段直推**：它声称「我尽力送达，超时重试」，但可靠性边界止于什么、漏在哪，是本报告要实证的。

---

## 2. EMQX 侧信封机制（配置解读，实证基础）

从 EMQX /api/v5/actions 实测 `fwd_telemetry`（类型 http）：

| 配置项 | 值 | 含义 |
|--------|-----|------|
| `max_retries` | 2 | HTTP 投递失败最多重试 2 次 |
| `inflight_window` | 100 | 最多 100 个在飞请求（超过则进缓冲） |
| `max_buffer_bytes` | 256MB | 缓冲上限，超限按策略丢弃新消息 |
| `query_mode` | async | 异步投递，返回即异步排队 |
| `request_ttl` | 45s | 请求在飞超过 45s 判失败（触发重试/放弃） |
| `worker_pool_size` | 16 | 投递并发线程 |

**关键解读**：EMQX 端「可靠」仅覆盖到**拿到 HTTP 2xx**。拿到了 200 = EMQX 认为成功，信封丢弃，不再重试。这决定了它看不到 200 之后发生了什么。

## 3. 场景论证（三路实测）

### 场景 1 · 队列打满：返回 200 但业务静默丢弃，EMQX 不重试

**触发条件**：上报速率 > 应用写路径稳态平台（C4 实测 ~248 msg/s）。

**复现（T4 档）**：

| 度量 | 值 | 来源 |
|------|-----|------|
| 输入端发布消息数 | 61,639 | 压测脚本 `published` |
| 后端入队被拒丢弃 | **27,694** | 应用 Meter `iot_telemetry_rejected_total` |
| 后端打回给 EMQX | **一律 HTTP 200** | Controller 入队成功即 200，丢弃在异步层 |

**推理**：27,694 条被应用静默丢弃，但每条都返回了 200 → **EMQX 认为全部成功，不会重试**。这是「打满即丢」最隐蔽的形态——**没有 4xx/5xx，没有失败告警（修复前「入库失败率」仍 0）**，只有把「丢」下沉到进程内队列的静默计数。

> 注：V2-C 第 2 轮已通过自定义拒绝策略把丢弃落成 `rejected_total` 指标，丢从此**可观测**；但「丢」本身依旧发生——这正是 Kafka 要消除的。

### 场景 2 · 后端重启：进程内在途丢，已 200 确认的消息永久缺失

**触发条件**：非优雅停机（kill/崩溃）时，进程内线程池队列仍有已确认未落库的任务。

**复现流程**：
1. T4 重压制造积压，kill 前 `queue_pending` gauge 采样到 **4,061 ~ 11,821 条**在途任务（压测中波动）。
2. `Stop-Process -Force` 硬杀后端（PID 16352），8080 断开。
3. 重启后端，db 恢复增长（见场景 3）。

**推理**：这 4,061~11,821 条是 **EMQX 已拿到 200（信封已丢弃）但应用尚未落库**的「在途」。进程强杀 → `ThreadPoolTaskExecutor` 的 **queue + 未执行任务全部随 JVM 丢失（无持久化、非优雅停机不落盘）**。且因为信封已丢，EMQX 永不重发这批 → **永久缺失**。
对比另一类「未确认」在飞消息会由 EMQX 缓冲重放——**同样在途，命运天差地别，全取决于「是否已被 EMQX 打上 200」**。

### 场景 3 · EMQX 缓冲重放边界：离线超时即放弃

**触发条件**：后端离线较久，EMQX 对未确认消息缓冲等待。

**复现**：宕机约 90s 后重启，观察 db：

| 时间点 | db 行数 | 说明 |
|--------|--------:|------|
| kill 前（pre_kill） | 400,273 | — |
| 重启恢复后（post_restart） | 426,724 | **+26,451** |

**推理**：宕机期间的**未确认消息**被 EMQX 缓冲，后端恢复后重放落库（+26,451 即重放量）——**前提是后端在 `request_ttl=45s` 窗口内恢复**。一旦离线持续 > 45s，超时消息被 EMQX 判定失败、按重试策略最终放弃 → 丢弃。且 `256MB` 缓冲满或 `max_retries=2` 用尽时，同样丢弃。**EMQX 的"尽力恢复"有一个明确的 TTL 上限。**

---

## 4. 边界总结：可靠性漏洞矩阵

| 丢的场景 | 谁在对什么「确认」 | 丢在 **AMQX 要不要负责** | 已确认消息归宿 | 是否有损 |
|---------|------------------|:--:|--------|:--:|
| S1 队列满静默丢 | 后端对入队确认(200)，EMQX 不再管 | C 不知情（以为成功） | **永久丢失** | ✅ 有损 |
| S2 后端重启丢在途 | 同上，进程内队列无持久化 | C 说尽力送达，不背锅 | **永久丢失** | ✅ 有损 |
| S3 离线 >45s/满缓冲 | EMQX 对 buffered 消息放弃重放 | C 重试窗口耗尽 | **永久丢失** | ✅ 有损 |

**根因一句话**：**确认语义错位**——「协议 200」被当作「业务成功」，但两者之间隔着无持久化的进程内队列和 TTL 有限的 EMQX 缓冲。任一环节异常，消息在“已确认”状态下消失，链路无感知。

---

## 5. 结论：为什么需要 Kafka

1. **持久化确认**：消息先落 Kafka（broker 落盘后才 ack 生产端），把「确认」从「上端 HTTP 200」下沉到「持久化已提交」，**S2 进程内队列丢失从源头消除**。
2. **解耦背压**：消费者按自己的写能力（~248 msg/s 平台）从容消费，**改由 Kafka 的 offset 记录进度，天然可丢转可重放**，S1「打满即丢」改为「积压待消费」。
3. **重试可靠**：S3 的 45s TTL 短板由消息留存补偿，后端恢复后从 offset 续消费，不靠脆弱的 TTL 猜窗口。
4. **成本提示**：相对 TDengine 直接解决写放大，Kafka 首要解决的是**可靠性语义**，二者在不同层面，需在 D 阶段结合《MySQL时序瓶颈分析报告》的成本/收益综合决策。
