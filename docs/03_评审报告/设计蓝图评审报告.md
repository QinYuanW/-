## 一、总评

设计蓝图三件套整体完成度高，比 schema 单项审核时又上了一个台阶：

1. **上轮审核全部闭环**：schema v1.2 已落实 6 项修复（REORGANIZE 滚月、四表软删、command 补 updated_at + idx_status_sent、product 补 project_id、value_type 默认 1），且在文件头部留了变更记录——这是好的工程习惯。
2. **「数据合同 → 接口契约」推导链成立**：契约附的「接口↔表字段对应表」把入参出参和表字段一一对上，前后端不会对不上字段。
3. **两个最容易踩的坑都提前讲了**：容器→宿主机用 host.docker.internal；REST API publish 的 payload 必须是字符串。
4. **但有一处关键技术错误（P0）**：鉴权回调的响应判定写成了 EMQX 4.x 协议，而 docker-compose 用的是 emqx:5.8。5.x 已做不兼容变更，照现契约实现，**凭据正确的设备也会被拒之门外**，D3 联调第一天就会卡死。

## 二、P0 · 必须修（写代码前）

### P0-1 鉴权回调响应协议错误（API契约 §0.3/§1 + EMQX配置 §2.3）

**问题**：契约规定「200 = 认证通过，403 = 认证拒绝」，时序图同样标注。这是 **EMQX 4.x 的判定协议**。

**官方文档事实**（docs.emqx.com《使用 HTTP 服务进行密码认证》）：

- 5.x 中认证结果由响应 body JSON 的 `result` 字段标示（`allow` / `deny` / `ignore`）；
- HTTP **204 = allow**；**4xx/5xx 会忽略 body，判定为 `ignore` 并继续认证链**（单认证器链最终默认拒绝）；
- 官方原文（兼容性说明节）：「在 4.x 中，EMQX 仅用到了 HTTP API 返回的状态码……例如 200 表示 allow，403 表示 deny。**因为缺乏丰富的表达能力，在 5.0 中对这一机制进行了不兼容的调整**」。

**后果推演**：若 SpringBoot 鉴权接口按契约返回 200 + 统一响应体 `{"code":0,"message":"ok"}`——EMQX 解析 body 找不到 `result` 字段，判为 ignore 而非 allow → **合法设备连接被拒**。403 虽然碰巧也会拒绝（ignore→链尾默认拒绝），但语义完全不对。

**修正后的契约（可直接替换 API契约 §1 响应表）**：

| 场景 | 状态码 | Body |
|------|:---:|------|
| 认证通过 | `204` | 无（推荐，最简单） |
| 认证通过（等价写法） | `200` | `{"result": "allow"}`（content-type: application/json） |
| 认证拒绝 | `200` | `{"result": "deny"}` |
| 服务异常（忽略交由认证链） | `4xx/5xx` | 忽略 body |

同步修改点：
- API契约 §0.3 第一条改述为「只看 HTTP 状态码」→「看 HTTP 状态码（204/200）+ body 的 result 字段」；
- EMQX配置 §2.3 时序图 `200(允许)/403(拒绝)` → `204 / {"result":"allow"}`、`{"result":"deny"}`；
- 契约 §1 业务逻辑第 2 条对应改写。

## 三、P1 · 建议修

### P1-1 规则 SQL 通配过宽（EMQX配置 §3.1）

`FROM "up/#"` 会匹配 `up/{device_key}/event`——事件报文也会被推给 `/api/v1/telemetry`，事件 payload 会被当属性写进遥测表（Topic 约定表里 event 是定义了的，测试时随手一发就污染数据）。
**修法**：`FROM "up/+/property"`（单层通配，只匹配属性上报）。

### P1-2 「认证缓存 TTL 60s」配置项存疑（EMQX配置 §2.2）

配置表把它列为认证器内的字段，但 EMQX 5.x 的认证结果缓存实为**节点级「External Resource Cache」**（Dashboard 认证页右上角全局开关：最大条数/最大内存/TTL，默认 1 分钟），且 EMQX Cloud 文档明确该特性 **5.9+**。项目镜像锁定 emqx:5.8，需实测 Dashboard 有无「External Resource Cache Settings」按钮：
- 有 → 开启即可，方案成立；
- 无 → 「防连接风暴第一道防线」只剩后端 Redis 凭据缓存（契约 §1 已有，可兜底），方案第 2.2 节相应改述；或镜像升到最新 5.x。

### P1-3 缺「历史遥测区间查询」接口（API契约 §3）

MVP 计划阶段 3 的完成标志是「浏览器里能看**温度曲线**」，但契约只有 latest 接口（3.2）。二选一：
- 补 `GET /api/v1/devices/{device_key}/telemetry?property=temperature&start=&end=`（走 idx_device_prop_ts 索引，顺手的事）；
- 或明确写「前端轮询 latest 自行累积数据点画曲线，刷新即清零」——能跑，但演示效果差。

### P1-4 缺「指令状态查询」接口（API契约 §4）

command 状态机设计了 0→1→2/3/4 终态，但控制台没有任何接口能查到终态——下发按钮点了之后永远不知道 LED 到底执行没执行、有没有超时。
**修法**：补 `GET /api/v1/commands/{request_id}`，返回 `{status, sent_at, ack_at}`。

## 四、P2 · 记录不修（避免后期反复讨论）

1. **编号不一致**：EMQX配置 §4 写「接口 5（控制下发）」，契约里下发是接口 4。
2. **telemetry 接口无鉴权**：内网任何主机可向 :8080 POST 伪造上报。MVP 接受；V2 在 Webhook 连接器 Headers 加静态 token + SpringBoot 校验（十分钟工作量）。
3. **无 topic 级 ACL**：设备 A 认证通过后可伪造发布 `up/B/property`，数据记到设备 B 头上。MVP 接受；V2 用 EMQX 授权（或 5.8+ 认证响应体的 acl 字段：只允许发/订自己的 `up/{device_key}/#`）。
4. **3.2 响应缺 ts/device_key**：前端想显示「最后上报时间」没有数据源。
5. **缺 login 接口**：契约说「D8 加 JWT」但没定义登录端点；user 注册/D11 设备注册+CSV 也未列。建议契约尾部加「遗留接口清单」一节统一标注，避免误以为 5 个 endpoint 就是全部。
6. **init-user.sql 注释不准**：「8.0 默认 mysql_native_password」——8.0 默认实为 caching_sha2_password，跨版本使用需 `IDENTIFIED WITH mysql_native_password BY`。本地 5.7 不受影响。
7. **docker-compose**：EMQX 容器无健康检查（Redis 有）；admin/public 默认密码起服即改；容器→宿主机 8080 可能被 Windows 防火墙拦（D3 排障优先怀疑这一点）。

## 五、通过项（确认无问题）

1. **三件套交叉一致性**：凭据（dev_demo_001 / demo_secret_123）、回调 URL（/api/v1/auth、/api/v1/telemetry）、Topic（up/down 约定）、ts 毫秒语义（EMQX 规则引擎 timestamp 即毫秒，与契约「毫秒时间戳转 DATETIME(3)」一致）、端口 18083——全部对齐。
2. **schema v1.2 修复闭环**：上轮 2 P0 + 4 P1 全部落实且留有变更记录；MySQL 5.7 兼容性（JSON ≥5.7.8 / DATETIME(3) 默认值 / RANGE COLUMNS 分区 / utf8mb4）逐项过关。
3. **seed.sql 幂等设计**：固定 id + ON DUPLICATE KEY UPDATE，可重复执行；user 不预置的理由（BCrypt 无法离线生成）正确。
4. **verify.sql 与 v1.2 逐项对齐**：7 表/13 分区/分区裁剪 EXPLAIN/软删 4 表/idx_status_sent/演示数据，六段核验覆盖到位。
5. **网络拓扑表**（host.docker.internal 双向）与 **publish payload 字符串坑**——两个 Docker + EMQX 联调最大坑都提前写明了。
6. **docker-compose 架构决策自洽**：EMQX 5.8 + Redis 7.2 入容器、本机 MySQL 5.7 不进容器避端口冲突，与 D1 已拍板决策一致。
7. **错误码/统一响应/异步削峰（有界队列）/QoS=1 建议**等接口层约定合理，无过度设计。
