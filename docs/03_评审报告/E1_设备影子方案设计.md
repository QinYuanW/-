# E1 · 设备影子（Device Shadow）方案设计

| 项目 | 内容 |
|------|------|
| 阶段 | V2-E · 平台核心能力 |
| 任务定义 | E1：**Redis 存储期望值/上报值，离线指令在设备上线后自动下发** |
| 设计依据 | 现有 `CommandServiceImpl` / `TelemetryServiceImpl` / `DeviceServiceImpl` 代码取证；需求 §物模型与设备管理 |
| 日期 | 2026-09-11 |
| 结论 | 方案可实施。**核心洞察：不需要新造队列，复用 `command` 表既有的 `status=0 待下发` 态即可**；影子只新增 Redis 一层 |

---

## 一、现状取证：E1 要填的洞（有代码证据）

### 1.1 离线指令 = 假成功 → 静默蒸发

`CommandServiceImpl.dispatch()` 的现有三步：

```
① 落库 status=0
② emqxClient.publish("down/{deviceKey}/command", message)   ← 无条件推送
③ published ? status=1(已下发) : status=3
```

**问题**：MQTT publish 是 fire-and-forget —— **设备离线时，EMQX 对无人订阅的 topic 依然返回成功**，于是：

```
离线下发 → publish 成功 → status=1(已下发)  ← 谎报
       → 设备从未收到
       → 60s 后被 timeoutScan 置 status=4(超时)
```

**结果**：离线指令既不重试、也无队列，**只能变成一条"超时"记录**。这与 D2-2 修的 BUG-21 是同一类病（"假成功"掩盖真实失败），只是从消费端换到了下发端。

### 1.2 在线/离线状态的既有机制（可直接复用）

| 转换 | 位置 | 触发 |
|---|---|---|
| `0 → 1` 上线 | `TelemetryServiceImpl.refreshOnline()` | 收到上报（5s 窗口聚合，Redis SETNX 协调） |
| `1 → 0` 离线 | `DeviceServiceImpl.offlineScan()` | `@Scheduled(30s)`：`online=1 且 last_online_at < now-OFFLINE_TIMEOUT` → 置 0 + 写下线日志 |

> **`refreshOnline` 的 `transitioned > 0` 分支 = 天然的"设备上线"事件钩子** —— E1 的影子同步就挂在这里，不需要引入 EMQX 上下线 Webhook。

### 1.3 可复用的既有资产

- `command` 表已有**状态机**：`0 待下发 / 1 已下发 / 2 已执行 / 3 失败 / 4 超时`
- `command` 表已有索引 **`idx_device_status_time (device_id, status, created_at)`** → **天然支持"查某设备所有 status=0 的指令"**
- `command.request_id` 唯一键 → 下发幂等已有基础
- 设备固件（ESP-IDF）**已实现** `down/{device_key}/command` 的解析与 ACK

---

## 二、目标与范围

**做**：期望值(desired)/上报值(reported) 的 Redis 存储 + delta 计算 + **离线指令上线自动补发** + 控制台可读写影子。

**不做**（避免范围蔓延）：影子的 MySQL 冷存/审计表、多设备影子批量下发、影子版本号与冲突解决（LWW 足够）、EMQX 上下线事件 Webhook（沿用现有扫描）。

---

## 三、关键设计决策（DP）

### DP-1 影子存储：Redis 单 Hash，双前缀 field

```
shadow:{deviceKey}                    (Hash)
  ├─ desired:temperature   = 26
  ├─ desired:switch        = "on"
  ├─ reported:temperature  = 24
  └─ reported:humidity     = 55
```

- **单 key + field 前缀**（而非拆成 `shadow:desired:*` / `shadow:reported:*` 两个 key）：
  一次 `HGETALL` 就能拿全量并**本地算 delta**，避免两次往返 + 跨 key 不一致。
- 持久化：Redis 已开 `appendonly yes`，够用。**不新增 MySQL 表**（理由见 §二"不做"）。

### DP-2 🔑 离线指令队列：**复用 `command` 表 status=0，不新造队列**

| 方案 | 评价 |
|---|---|
| A. 新增 Redis List `pending:cmd:{key}` | 要自己实现持久化/去重/状态同步 → 与 `command` 表**双写不一致**风险 |
| **B. 复用 `command` 表 `status=0`** ✅ | 零新增存储；状态机/索引/request_id 幂等**全部现成**；指令生命周期仍在**同一张表**里可追溯 |

**改造点仅一处**：`dispatch()` 第②步加"在线判定闸门"：

```
落库 status=0
   ├─ 设备在线 → publish → status=1（原逻辑）
   └─ 设备离线 → 不 publish，保持 status=0  ← 新增分支
```

> **面试叙事**：这里没有为了"离线队列"再造一个中间件，而是**复用了既有状态机里本就存在的 `0 待下发` 态** —— 让状态的语义缺口（"0 态此前几乎一闪而过"）变成功能载体。

### DP-3 上线触发点：`refreshOnline` 的 0→1 分支

```
设备上线（0→1）
   └─ shadowSync(deviceId, deviceKey)
        ├─ ① 补发：SELECT * FROM command WHERE device_id=? AND status=0 ORDER BY created_at
        │        → 逐条 publish → 成功置 1 / 失败置 3     （走 idx_device_status_time）
        └─ ② 对齐：delta = desired − reported 非空时，下发 property_set 指令
```

- 放在 `refreshOnline`（而非新建调度）**零额外轮询开销**。
- 补发与 delta 对齐**在同一线程串行**，保证下发顺序 = 指令创建顺序。

### DP-4 reported 更新：挂在遥测写路径的**旁路**上

在 `TelemetryServiceImpl.processSync()` 的 `insertBatch` 之后追加影子更新：

- **纪律（沿用 D2-2）**：`try/catch` 包裹，**失败只计数（`iot_shadow_write_failures_total`）、绝不上抛** —— 影子是增强能力，**不能因它把主链路遥测打进 retry/DLT**。
- 优化：**只更新 TSL 中声明的属性**（读 `device.tsl` 过滤），避免设备上报的临时/未知 key 污染影子。

### DP-5 MQTT 下行：复用现有 topic，不改固件

- desired→设备仍走 **`down/{device_key}/command`**，`command_type = "property_set"`。
- **理由**：固件（ESP32-S3，ESP-IDF）已实现该 topic 的解析 + ACK；新增 `down/{key}/shadow` 需要**同步改固件并重新烧录** → 成本高、风险大，收益仅"语义更清晰"。
- 备注：全量影子对齐（`down/{key}/shadow`）列为**后续可选增强**（F1 OTA 若要复用影子做状态载体再评估）。

### DP-6 在线判定口径

以 `device.online_status` 为准（15s 上报周期下，`OFFLINE_TIMEOUT` 已覆盖）。**不在 `dispatch` 里额外查 Redis 在线标记** —— 单一事实来源，避免两套在线口径打架。

## 四、接口契约（新增 3 个，均在 `/api/v1/**` 鉴权保护内）

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/devices/{deviceKey}/shadow` | 返回 `{desired:{}, reported:{}, delta:{}}` |
| `PUT` | `/devices/{deviceKey}/shadow/desired` | body `{prop: value, ...}`；写入 desired → 若有 delta 则尝试下发；返回 `{updated:[...], dispatched:bool, request_id?}` |
| `GET` | `/devices/{deviceKey}/commands?status=0` | 查待下发指令（离线队列可视化，控制台用） |

## 五、核心时序：离线下发 → 上线自动补发

```
控制台        CommandService        Redis(shadow)      EMQX        设备
  │                │                    │              │           │
  ├─ PUT desired ─►│                    │              │           │
  │                ├─ HSET desired:x ──►│              │           │
  │                ├─ delta 非空? 设备在线?             │           │
  │                │   └─ 离线 → 只落 command(status=0)，不 publish  │
  │                │                                   │           │
  │                │           …… 设备上线，首条 telemetry ……        │
  │                │                                   │◄── CONNECT/上报
  │   TelemetryService.refreshOnline()  0→1 转换                     │
  │                ├─ shadowSync() ────────────────────►│           │
  │                │   ├─ 补发 status=0 指令 ──────────►├─ publish ►│
  │                │   └─ 下发 delta ──────────────────►│           │
  │                │                                   │◄── ACK ───┤
  │                ├─ command status: 0 → 1 → 2 ✅      │           │
```

## 六、风险与待确认

| 级别 | 项 | 处置 |
|:--:|---|---|
| 🟡 P1 | **reported 写放大**：每条遥测都 `HSET` 影子 → Redis 往返增加 | 先观望（Redis 本就在写路径上，`did:` 缓存已占一次往返）；若成为瓶颈，改用 pipeline 批量。**B5 埋点已能观测**，有据可依 |
| 🟡 P1 | **补发风暴**：设备长时间离线积累大量 status=0 指令 → 上线瞬间全量下发 | 加**补发上限**（如单次最多 N 条，其余保留 status=0 下轮继续）+ `MAX_TTL` 过期（超 24h 的待下发指令直接置 4 超时） |
| 🟡 P1 | **指令执行后 desired 是否回落**：设备 ACK 成功(2) 后，desired 是否等于 reported？ | **保持独立**（desired=意图，reported=实际）。若设备上报值与 desired 不一致，影子如实呈现 delta —— 这**正是影子的价值**（暴露不一致），不做自动抹平 |
| 🟢 P2 | **并发**：控制台改 desired 与设备上报 reported 同时 | 不同 field，Redis Hash 单 field 写原子，无需锁 |
| 🟢 P2 | **补发的幂等**：上线瞬间重复触发 shadowSync | 靠 `command.request_id` 唯一 + 状态机条件更新（`eq(status,0)`）天然幂等 |
| ❓ | **待确认**：`OFFLINE_TIMEOUT_SECONDS` 当前取值；固件是否支持 `property_set` 指令类型 | 实施 T1 时核对 `DeviceServiceImpl` 常量 + `firmware/esp32_iot/main/iot/platform_mqtt.c` |

## 七、验收标准（可取证）

| # | 场景 | 期望（取证方式） |
|---|---|---|
| 1 | 设备**离线**时下发指令 | `command.status` 保持 **0**（不再谎报 1）；**不产生** publish |
| 2 | 设备随后**上线**上报 | 指令被自动补发 → status `0→1→2`；`device_log` 有上线记录 |
| 3 | 在线时下发 | 与现状一致：直接 `0→1`（无回归） |
| 4 | 影子读写 | `GET shadow` 返回 desired/reported/delta 三者一致可核对 |
| 5 | **影子失败隔离** | 故意让 Redis 写影子失败 → 遥测**仍正常入库**、`iot_shadow_write_failures_total` 增长，**DLT 无新消息** |
| 6 | 补发上限 | 造 20 条离线指令 + 设上限 5 → 上线只下发 5 条，其余仍为 0 |

> 第 5 条是**必须验的一条** —— 它证明影子没有污染 D2-2 刚修好的主链路。

## 八、实施拆解（4 步）

| 步 | 内容 | 产出 |
|---|---|---|
| **T1** | 影子存储层：`ShadowService`（Redis Hash 读写 + delta 计算）+ 配置常量核对 | 单元可测的 `getShadow / setDesired / updateReported` |
| **T2** | 上报接线：`processSync` 旁路更新 reported（失败隔离 + 计数） | `iot_shadow_write_failures_total` |
| **T3** | 下发闸门 + 上线补发：`dispatch` 在线判定；`refreshOnline` 触发 `shadowSync`（含补发上限 / 过期） | 验收 1/2/3/6 |
| **T4** | 接口 + 控制台：3 个 API + 前端影子卡片（desired/reported/delta 三栏对比） | 验收 4；演示素材 |

> 控制台那栏（T4）是**演示视频的天然素材**：一边改期望值、一边看设备上线后自动对齐 —— 比纯讲后端有说服力。

## 九、与后续阶段的衔接

- **F1（OTA）依赖本任务**：OTA 状态（当前版本 / 升级进度）可作为影子的一类 desired/reported 属性承载，复用同一套同步机制。
- **E3（规则引擎）**：阈值触发指令下发时，若设备离线 → 直接复用 DP-2 的 status=0 队列，天然获得"离线也能触发"的能力。
