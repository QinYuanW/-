### 2.3 查询耗时（含 `mysql.exe` 进程启动开销，净 SQL 约减 0.3s）

| 查询 | 实测 | 净耗时（估） |
|---|---:|---:|
| `SELECT COUNT(*) FROM device_telemetry` | 0.585s | ≈0.25s |
| `SELECT DATE_FORMAT(ts,'%Y-%m') m, COUNT(*) c … GROUP BY m` | 0.765s | ≈0.45s |

### 2.4 表结构要点（影响可选优化）

```
PRIMARY KEY (id, ts)
UNIQUE KEY uk_device_prop_val_ts (device_id, property_key, value, ts)
KEY idx_device_ts (device_id, ts)
KEY idx_device_prop_ts (device_id, property_key, ts)
PARTITION BY RANGE COLUMNS(ts)  -- p202608 … p202707 + pmax（按月）
```

- ⚠️ **没有 `ts` 单列索引** → 全表 `COUNT(*)` / `GROUP BY` 走的是全分区扫描（当前 44 万行可接受）
- ✅ **但分区裁剪可用**：带 `ts >= 本月1号` 条件的计数**只需扫 1 个分区**，这是「本月/今日」两段的性能保障

## 3. 三个接口的实现设计

### 3.1 `GET /stats/overview` — 概览统计

```sql
-- 产品（小表，直接聚合）
SELECT COUNT(*) total,
       SUM(status = 1) enabled,
       SUM(status = 0) disabled
FROM product WHERE deleted = 0;

-- 设备（小表）
SELECT COUNT(*) total,
       SUM(online_status = 1) online,
       SUM(status = 1) enabled
FROM device WHERE deleted = 0;

-- 消息（大表，三段分别处理）
SELECT COUNT(*) FROM device_telemetry;                                    -- total：全表
SELECT COUNT(*) FROM device_telemetry WHERE ts >= '2026-09-01';           -- month：分区裁剪 ✅
SELECT COUNT(*) FROM device_telemetry WHERE ts >= '2026-09-14';           -- today：分区裁剪 ✅
```

**性能策略**：
- `product` / `device` / `device_log` 一律直查（合计 < 3300 行，忽略不计）
- `total` 是唯一的全表扫描 → **加 Spring Cache `@Cacheable(cacheNames="stats:overview", sync=true)`，TTL 5s**
- `month` / `today` 走分区裁剪，无需缓存

> **不引入 Redis 计数器**。理由：省下的 0.25s 换不来运维复杂度（重放/回滚会导致计数漂移，还得写对账脚本）。
> **留好退路**：若 D3 之前数据涨到千万级、`total` 超过 1s，再上计数器——**届时用 D5 的压测数据说话**。

### 3.2 `GET /stats/message-trend` — 趋势

**建议改为按天**（`?days=30`）：

```sql
SELECT DATE(ts) d, COUNT(*) c
FROM device_telemetry
WHERE ts >= DATE_SUB(CURDATE(), INTERVAL 30 DAY)
GROUP BY d ORDER BY d;
```

**理由**：数据只在 2026-09 → 按月输出会是「1 根柱子」；按天能画出 30 根，演示效果天差地别。

**同时保留按月能力**（`?granularity=month&months=12`），供 D3 迁移后数据积累起来再切回：
```sql
SELECT DATE_FORMAT(ts,'%Y-%m') m, COUNT(*) c
FROM device_telemetry WHERE ts >= ?
GROUP BY m ORDER BY m;
```

> ⚠️ **只返回有数据的桶，缺失的由前端补 0** —— 后端不构造空桶，保持接口"笨"。

### 3.3 `GET /alerts` — 告警列表

**本期只交付"能通不报错 + 返回空列表"**，数据写入依赖 E3。

- 响应结构按契约 §7.3 定型（`total` / `types` / `items`）
- 数据源建议独立 `device_alarm` 表（含 `status` 状态流转），**不复用 `device_log`**（1024 字符自由文本，筛选统计会退化成字符串解析）
- **表结构随 E3 落地**，E6 阶段先返回空数组

## 附 · 与 D3/D5 的衔接

本次实测的 **0.25s（COUNT）/ 0.45s（按月聚合）** 就是 D5 报告「查询 RT」组的 **MySQL 侧基线**。

D3 迁移到 TDengine 后，用**同样的三个查询**跑一遍 → 直接得出对比表格。**这就是当初把 E6 排在 D3 之前的全部理由**：没有这份基线，D5 报告就只剩"写入吞吐 + 压缩比"两条腿。

**查询 RT —— D5 的 MySQL 侧基线**

| 接口 | 实测（6 次） | 中位 | 说明 |
|---|---|---:|---|
| `/stats/overview` | 782–852ms | **799ms** | 内部 **8 次独立查询**（2 产品 + 3 设备 + 3 消息） |
| `/stats/message-trend` | 642–766ms | **702ms** | 1 次聚合查询 |
| `/alerts` | 5ms | — | 空壳 |

> ⚠️ **实测比预估慢约 3 倍**（预估 COUNT 0.25s → 实测 overview 0.8s）。原因**不是 SQL 慢，而是 `overview` 发了 8 次独立查询**，每次都有 JDBC 往返，累加起来了。
>
> **已知优化空间（本次刻意不做）**：把 8 个 COUNT 合并成 1 条 SQL（`SELECT (SELECT …) a, (SELECT …) b …`）可将往返压到 1 次，预计 RT 减半。
> **不现在做的理由**：D5 要比的是"**同等工作量下的引擎差异**"。MySQL 侧保留常规实现，才是公平起点；若先手工优化到极致，对比的就成了"我优化了多少"而不是"引擎本身差多少"。该优化项作为"D5 时 MySQL 侧优化上限"的补充对照保留。

**前端**：`Dashboard.vue` 去 mock 完成；顺带修掉一处**照 mock 量级硬编码的 `yAxis.max: 2300000`**（真实数据最大 41.59 万，会被压成一条扁线）。
