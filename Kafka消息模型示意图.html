② 同一主题 + 不同消费者组 = 两种消息语义

Group A：order-service（同一组）
消费者 A1 → P0
消费者 A2 → P1、P2
队列 / 点对点语义
同组内分摊分区，一条消息只被组内一个消费者处理，不重复消费
Group B：audit-service（不同组）
消费者 B1 → P0、P1
消费者 B2 → P2
发布 / 订阅语义
每个组各自维护 offset，各自消费全量数据，互不影响

③ 与常见中间件的定位对比

Kafka
主题 + 消费者组 → 同时具备队列与发布订阅语义；高吞吐、可回溯、持久化
MQTT
纯发布/订阅，经 Broker 按主题路由，轻量，面向 IoT 设备
RabbitMQ
队列为主 + 交换机路由，灵活但吞吐低于 Kafka

④ 两个易误解的点

消息是"拉"不是"推"：消费者主动向 Broker 拉数据，处理速度自己掌控，天然支持批量消费；
消息不会消费完就消失：持久化在分区日志里，靠 offset 记录进度，可重置 offset 从头回溯重读 —— 这也是 Kafka 能做流处理和事件溯源的基础。
